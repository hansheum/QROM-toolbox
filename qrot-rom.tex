  Let us begin by introducing our motivating public-key encryption scheme
    $\brescheme$ (for ``Bellare-Rogaway Encryption''), which will follow us
    throughout as we explore the world of O2H lemmas. It is a hybrid public-key
    encryption scheme, meaning that it is built from a Key Encapsulation Mechanism (KEM) and a
    Data Encapsulation Mechanism (DEM). 

  Two differences from the canonical
    hybrid encryption construction: First, the symmetric key is not used as-is,
    but rather derived by hashing the key that was output by the KEM (in the literature
    on the Fujisaki-Okamoto transformation~\cite{C:FujOka99} this step is known as
    the ``U transform''~\cite{TCC:HofHovKil17}); secondly, the
    DEM is taken to be the One-Time Pad (OTP).\footnote{
      Information-theoretical DEM security
      is not actually required for the proofs to go through, 
      but using the OTP significantly simplifies our analyses.
    } 

  The algorithms of $\brescheme$ are specified in \autoref{fig:bre}. The public parameter
    generation algorithm $\brepm$ and the keypair generation algorithm $\brekg$
    are inherited from the underlying KEM, while the encryption algorithm
    $\breenc$ and the decryption algorithm $\bredec$ are as outlined above: When
    encrypting, the symmetric key $\demkey$ is used as a seed to the random
    oracle $\RO$ together with the encapsulation $\ctxt$ and the public key
    $\pk$, yielding a random string $\rnd$.\footnote{
      Hashing the public key $\pk$ and encapsulation $\kemctxt$ is not strictly necessary for 
      security to hold, but including them lets us write tighter security 
      proofs in the multi-user, multi-challenge setting.
      Generally, you could do worse than follow the principle ``hash everything possible''.
    } This is then used as a one-time pad, encrypting the message $\mssg$ by
    xoring with $\rnd$. For decryption, $\rnd$ is re-computed and the xor
    operation is repeated, revealing $\mssg$.

  This simple PKE scheme 
    %and its CCA-secure variants (where CCA security is usually achieved by adding
    %a MAC to the encryption process, which is then verified during decryption), 
    was first analyzed by Bellare and
    Rogaway in their seminal paper ``Random Oracles are
    Practical''~\cite{CCS:BelRog93},
    %\footnote{
    %  If you still haven't read Bellare and Rogaway's masterful introduction of
    %  random oracles to provable security, do so now! Go on, I'll wait.
    %} 
    and variants have shown up in many contexts since,
    including as the REACT transform~\cite{RSA:OkaPoi01}, as non-committing
    encryption~\cite{C:Nielsen02a,CSF:CLNS17}, in the study of
    selective-opening attacks~\cite{PKC:HJKS15,AC:LYHW21}, and 
    of security against mass surveillance~\cite{PKC:BruHeuSta24}. We refer to it as
    Bellare-Rogaway Encryption (BRE).\footnote{
      Technically, BRE is not \emph a scheme, but rather a class of schemes or
      a construction \emph{paradigm}, in much the same way that ``hybrid encryption'' is,
      since there is some variance in what elements are hashed, as well as how
      to expand the scheme to achieve CCA security, for example through an
      encrypt-then-mac construction.
    }

  At a glance, hashing the symmetric key to derive another symmetric key may seem completely
    unnecessary: By assumption, $\demkey$ was already drawn with
    high enough entropy, so that hashing it only has the effect of replacing
    one random string with another. And yet, forcing the key to go through
    a random oracle allows our reduction to learn the value of the key,
    which in turn will allow us to weaken the security assumption
    from indistinguishability to one-wayness. 

  \subsection{PKE Preliminaries}
    Let us define a few conventions. First, whenever a value is generated
      dependent on some other public value, such as the public key $\pk$ being
      dependent on the public parameters $\params$, which in turn depend on the
      security parameter $\secpar$, we assume without loss of generality that
      the derived value includes descriptions of the priors (so if you
      know $\pk$, then you also know $\params$, and so on). Similarly, we assume
      that if you know a secret key $\sk$ belonging to a keypair $(\pk, \sk)$, then 
      you also know $\pk$. This is without loss in the sense
      that after key generation, one can always define the keypair to be
      $(\pk, (\pk, \sk))$ (though note that this enforces a
      unique-public-key relation, since now each private key will correspond to
      exactly one public key).\footnote{
        There exist PKE schemes that violate this uniqueness relation, and
        some security proofs even exploit this~\cite{EC:BelHofYil09}.
      }

    Adversaries are assumed to be generally quantum agents, having
      access to as much classical and quantum memory as they need, on which
      they can apply unitary operations and measurements as they
      please. (We will come upon cases later where it will be beneficial to restrict this
      assumption.) We will mostly think of these agents as being \emph{efficient} in the sense of
      running in time polynomial in the security parameter $\secpar$, although
      we will stick with a concrete formal treatment wherein asymptotics are
      avoided, and the running time of reductions are instead stated directly in terms
      of the running time of the original adversary. We may also
      consider \emph{unbounded} adversaries; these can be thought of as running
      in time (and space) exponential in the security parameter.

    If the adversary $\adv$ has access to a random oracle $\RO$, this is
      written $\adv^{\RO}$, and likewise for any other oracles it may have
      access to. (Our notation does not distinguish between quantum and
      classical oracles.) Similarly, if a reduction $\bdv$ has black-box access
      to an adversary $\adv$ (meaning it may control its input and read its output, but not
      otherwise read or affect its internal workings), this is written $\bdv^\adv$.

  \subsubsection{Defining security.}
    The standard security notion for public-key encryption is usually taken to
      be ``Indistinguishability under Chosen-Ciphertext Attacks'', or $\indcca$,
      but for the sake of this tutorial we will stick to the weaker 
      ``Indistinguishability under Chosen-\emph{Plaintext} Attacks'' ($\indcpa$). Since
      this is a public-key encryption scheme, the chosen-plaintext attacks can
      be performed ``offline'' by the adversary simply by running the
      encryption algorithm itself using the provided public key. 
      %Therefore, unlike in the symmetric encryption case, we do not need to provide 
      %the adversary with an honest encryption via an oracle.
      % Eh, it gets this anyway, by letting m0 = m1, making the point moot.

    On the left of \autoref{fig:ind-ow} is the experiment
      defining our (single-user) $\indcpa$ security notion. The game starts by sampling
      parameters $\params$, a keypair
      $(\pk,\sk)$, and a challenge bit $\chalbit$, before handing the public
      key to the adversary $\adv$. If the construction in question uses a
      random oracle $\RO$, then $\adv$ also gets oracle access to $\RO$. 

    At some point, the adversary decides on two equal-length messages
      $\mssg_0$ and $\mssg_1$, and call its \emph{challenge encryption} oracle $\Oenc$
      (\autoref{fig:ind-ow}, middle). This oracle then provides an honest
      encryption of the message $\mssg_{\chalbit}$ and returns a challenge
      ciphertext $\chalctxt$. If the adversary ever calls
      the challenge oracle on messages of differing lengths, then it returns the
      special ``fail'' symbol $\fail$ instead; this is due to the
      assertion that a scheme should be considered
      secure even if ciphertexts leak information about message lengths.
      In fact, you may notice from \autoref{fig:bre} that
      our BRE scheme leaks the message length exactly, since $\demctxt$
      must necessarily have the same length as $\mssg$. 
      
    We are in the \emph{multi-challenge} setting, and so the adversary may
      continue to make as many calls to $\Oenc$ as it likes,
      in addition to arbitrary calls to the random oracle $\RO$. 
      (If the adversary is restricted to a single call to $\Oenc$, we call this
      the \emph{single-challenge setting}.)
      Once it is satisfied, $\adv$ halts with a guess $\advbit \in
      \bin$, and wins if it guessed $\chalbit$ correctly.

    We measure security in terms of $\adv$'s \emph{distinguishing advantage},
      i.e.\ how much better it can do than random guessing.

    \begin{definition}[Distinguishing Advantage]
      The distinguishing advantage of an adversary $\adv$ against a
        public-key encryption scheme $\pkescheme$, under chosen ciphertext
        attacks, is defined as
      \begin{align*}
        \advantage{\indcpa}{\pkescheme} &\coloneqq \abs{
          2 \cdot \prob{\experiment{\indcpa}{\pkescheme}} - 1
        }\, ,
        \intertext{or, equivalently,}
        \advantage{\indcpa}{\pkescheme} &\coloneqq \abs{
          \prob{\experiment{\indcpa}{\pkescheme}} 
          - \prob{\neg\experiment{\indcpa}{\pkescheme}}
        }\, ,
        \intertext{or, equivalently,}
        \advantage{\indcpa}{\pkescheme} &\coloneqq \abs{
          \condprobsample{
            \experiment{\indcpa}{\pkescheme}
          }{0 \sample \adv}{\chalbit = 0}
          - \condprobsample{
            \experiment{\indcpa}{\pkescheme}
          }{0 \sample \adv}{\chalbit = 1}
        }\, .
      \end{align*}
      where $\experiment{\indcpa}{\pkescheme}[]$ is as given in
      \autoref{fig:ind-ow}.
    \end{definition}

    \noindent
    As is easiest seen from the first of the above three equations, the
      advantage is just the probability that $\adv$ wins the game, minus the
      probability of winning based on a random guess, scaled so that the
      advantage is a value defined on the interval from $0$ to $1$,
      where $0$ means $\adv$ has no advantage (e.g.\ if the messages are perfectly hidden), 
      and $1$ means that $\adv$ is a perfect distinguisher (the scheme is
      completely broken, or $\adv$ is unbounded).

  \subsubsection{Kinds of reductions.}
    We say that a reduction is \emph{simple} if it only runs the adversary once,
      and \emph{fully black-box} if it runs the adversary from start to finish,
      answering oracle queries along the way, and otherwise only providing its
      input and reading its output; if, as is typically the case, the reduction
      is both simple and fully black-box, we call it an SFBB reduction. 

    We will later see some reductions that \emph{rewind} the adversary, and run
      it again from a point chosen by the reduction. We model this as the usual
      black-box access with an additional rewinding \emph{interface}, with which
      it can essentially tell the adversary to rewind itself to a specified point
      in its computation; we refer to it as a \emph{rewinding black-box} (RBB)
      reduction.

  \subsection{From One-wayness to Indistinguishability}\label{sec:bre-classical}
    It is time to prove our first theorem.

    %\newcommand{\kemRed}{\Red{\kemscheme}}
    \newcommand{\pkeEve}{\adv}
    \newcommand{\kemRed}{\bdv}
    \begin{theorem}\label{thm:bre-classical}
      Let $\kemscheme$ be a key encapsulation mechanism, let $\brescheme$ be the
      public-key encryption scheme defined in \autoref{fig:bre}, and let $\RO$ be a random oracle. 
      Then there is a SFBB reduction $\kemRed$ against $\kemscheme$ 
      for every adversary $\pkeEve$ against $\pkescheme$ making at most $\qRO$
      calls to the random oracle, such that
      \[
        \advantage{\indcpa}{\brescheme}[(\pkeEve^{\RO})]
        \leq 2\cdot\qRO\cdot \advantage{\owcpa}{\kemscheme}[(\kemRed)]
      \]
      in the classical random oracle model. The runtime of $\kemRed$ is equal
      to that of $\pkeEve$, plus the overhead of lazy-sampling $\qRO$ calls to
      the random oracle. 
      If $\pkeEve$ makes $\qe$ calls to the challenge
      oracle, then $\kemRed$ makes $\qe$ calls to its own challenge oracle.
    \end{theorem}

    \iftutorial
    \paragraph{Interpretation.}
      Before proving the theorem, let us take a look at what the statement
        actually tells us.
        The first thing to note is the order of the quantifiers: There exists
        ($\exists$) a simple, fully black-box reduction
        $\kemRed$ for all ($\forall$) adversaries $\pkeEve$. At a glance, this
        may seem false, since the behaviour of $\kemRed$ depends on the behaviour
        of $\pkeEve$. However, since $\kemRed$ only
        depends on $\pkeEve$ in a \emph{black-box} manner, what we are actually
        saying is that \emph{up to} this black-box dependency, $\kemRed$ can
        be uniquely specified. (Another way to think of this is that $\kemRed$
        comes with a number of oracle input/output interfaces, with one slot
        reserved for an adversary.)

      Second, what does the bound actually tell us? Well, our starting assumption is that
        the key encapsulation mechanism is sufficiently one-way secure under chosen plaintext
        attacks, which means that, for all adversaries,
        $\advantage{\owcpa}{\kemscheme}[(\kemRed)]$ is
        small. Then, $\advantage{\indcpa}{\brescheme}[(\pkeEve^{\RO})]$
        must also be small. 
        (In the asymptotic-security framework, we would say that 
        by assumption, $\advantage{\owcpa}{\kemscheme}[]$ is
        \emph{negligible}, i.e.\ smaller than any inverse-polynomial. Then the
        bound tells us that $\advantage{\indcpa}{\brescheme}[]$ must
        also be negligible, and hence $\brescheme$ must satisfy
        indistinguishability against chosen-ciphertext attacks.) 

      Or vice versa:
        \emph{If} there exists an adversary that breaks the indistinguishability
        of $\pkescheme$, \emph{then} we can construct an alternative attacker
        that breaks the onewayness of the underlying key encapsulation
        mechanism, contradiction our starting assumption.
        Of course, in order to argue that $\kemscheme$ satisfies onewayness, we
        would have to further reduce it to some underlying hardness assumption,
        but those are their own whole fields of study. Indeed, ``pushing'' the
        required security assumption as far down as possible, as we do when reducing
        from indistuinguishability (stronger) to onewayness (weaker), makes
        instantiating our scheme from a variety of hardness assumptions that
        much easier.
        %\footnote{
        %  To quote Hugo Krawczyk~\cite{KrawczykDistLect23}: 
        %  ``Modularity is the best friend of simplicity.''
        %}

      Third, notice that the right-hand-side comes with a factor $2\cdot \qRO$; 
        we call this the \emph{tightness loss} of the theorem. If we take the
        upper bound on the number of calls to the random oracle $\qRO$ to be $2^{80}$,
        a common estimate for the number of times the standard hashing algorithm
        SHA3 has been run since it was introduced, and we want a guarantee that 
        the distinguishing advantage of $\brescheme$ is less than, say,
        $2^{-128}$, then we need to set the parameters of $\kemscheme$ such that
        $\advantage{\owcpa}{\kemscheme}$ is guaranteed (via a lower-level reduction to
        the underlying hardness assumption) to be less than $2^{-209}$ (since
        $2\cdot 2^{80}\cdot 2^{-209} = 2^{-128}$).
        Increasing parameters come at the cost of efficiency, with increased
        key- and ciphertext lengths. Therefore, we really want to minimize the
        tightness loss in order to make the scheme practically efficient without
        sacrificing formal security guarantees.\footnote{
          Quantifying and minimizing tightness losses is the main motivation of the
          concrete-security paradigm, as these losses are all polynomial
          in the security parameter and hence irrelevant to
          asymptotic security, yet are clearly of consequence to practical
          implementations of the scheme.
        }
        
      Fourth, note that in the statement, $\pkeEve$ gets access to a random
        oracle $\RO$ while $\kemRed$ does not. This is because $\kemRed$ can
        easily simulate a random oracle for $\pkeEve$ by so-called
        ``lazy-sampling'', in which $\kemRed$ just samples random values for
        each new oracle call, and then stores them in a list to ensure
        consistency between calls, as explained in \autoref{sec:prelim}. 
        We could alternatively give $\kemRed$ access
        to a random oracle as well, and let it simply forward the oracle calls
        (once we move to the quantum random oracle model, this will be the
        preferred approach).

      Finally, in order for the bound to be meaningful, we also need to bound
        the runtime of our reduction. In this case, this is the runtime
        of the adversary itself, plus the overhead cost of lazy-sampling the
        random oracle, which we can assume is comparatively small.
    \fi

    \paragraph{Proof sketch.}
      \autoref{fig:bre-classical-games} provides an overview of the game hops that
        make up the proof of \autoref{thm:bre-classical}.
        For the first game hop, note how $\game{0}$ and $\game{1}$ are identical,
        except for the real symmetric key being exchanged for a random one. This
        is reminiscent of the IND-CPA experiment for KEMs, in which the
        adversary is tasked with distinguishing a real from a random key, given
        an encapsulation of the random key;
        and indeed, if $\pkeEve$ can tell the difference between the
        two games, then a reduction could use this to break $\indcpa$ for the
        underlying KEM.

      However, since we are in the random oracle model, we can do one better: If
        $\pkeEve$ can tell the difference between $\game{0}$ and $\game{1}$, then 
        a reduction can break the \emph{one-wayness} of the underlying KEM,
        recovering the complete symmetric key $\demkey$ with high probability. 
        How? Simple: Just store the adversary's inputs to the random oracle, and
        output one of them at random in the end.
        If $\pkeEve$ has a non-trivial distinguishing strategy, then that strategy must
        involve calling the random oracle on the symmetric key encapsulated in
        $\kemctxt$, since the only way to tell the two games apart is by breaking
        $\kemctxt$, reconstructing $\demctxt$, and checking for consistency.
        Then, since $\pkeEve$ makes at most $\qRO$ calls to the random oracle,
        the reduction will output the correct value with probability at least
        $\nicefrac{1}{\qRO}$.

      The second game hop switches the challenge bit of the indistinguishability
        experiment from $\chalbit=0$ to $\chalbit=1$; with the DEM ciphertext
        now independent from the KEM encapsulation, and since we chose the
        one-time pad as our DEM, this change is completely imperceptible
        to the adversary. Finally, having made this change, we switch back from
        random to real symmetric keys, repeating the argument from the first
        hop (this is where the factor $2$ comes from).
        The result is that we have gradually moved from the ``left'' to the ``right''
        world of the $\indcpa$ game, allowing us to bound the distinguishing advantage.

    \begin{proof}
      \iftutorial
      Though the reduction is conceptually fairly simple, you should
        make sure you thoroughly understand the details of the formal argument, 
        as the proof introduces much of the formalism we will 
        use to argue about security in the QROM.

      \fi
      The proof proceeds over three game hops, outlined in
        \autoref{fig:bre-classical}: 
      \begin{itemize}
        \item $\game{0}$ is identical to the ``left-world'' $\indcpa$ game,
          i.e.\ $\experiment{\indcpa}{\pkescheme}[]$ from \autoref{fig:ind-ow}
          when instantiated with the challenge bit $\chalbit = 0$, where we have
          also ``unrolled'' the BRE construction given in \autoref{fig:bre} (as
          well as explicitly lazy-sampling the random oracle).
        \item $\game{1}$ is the same as $\game{0}$, except that the symmetric key
          $\demkey$ output by $\kemenc$ is overwritten by an independent value,
          ensuring that $\rnd$ and hence $\ctxt_2$ is independent of $\ctxt_1$.
          If $\pkeEve$ ever calls the random oracle on the correct symmetric key
          $\demkey$ encapsulated as part of a challenge, then they can notice
          the inconsistency (since with overwhelming probability attempting to
          thereafter decrypt $\demctxt$ will yield neither $\mssg_0$ nor
          $\mssg_1$). This is captured by the $\bad$ event, which if ever hit
          upon causes the game to abort. Note how the random oracle ensures that
          $\game{0}$ and $\game{1}$ are identical from the view of the player
          unless and until the $\bad$ event is triggered.
        \item $\game{2}$ is the same as $\game{1}$, except that the challenge oracle
          now encrypts the ``right-world'' message $\mssg_1$.
        \item $\game{3}$ is the same as $\game{2}$, except that the symmetric key
          $\demkey$ is no longer overwritten, removing the need for a $\bad$ event,
          making $\game{3}$ identical to the ``right-world'' $\indcpa$ game when
          instantiated with the BRE construction.
      \end{itemize}

      \noindent
      We analyze the game hops using \autoref{lemma:game-hopping}:
      \begin{align*}
        \advantage{\indcpa}{\brescheme}[(\pkeEve)] &\coloneqq 
          \abs{
            \condprobsample{
              \experiment{\indcpa}{\brescheme}[(\pkeEve)]
            }{0 \sample \adv}{\chalbit = 0}
            - \condprobsample{
              \experiment{\indcpa}{\brescheme}[(\pkeEve)]
            }{0 \sample \adv}{\chalbit = 1}
          } \\
        &= \abs{
          \probsample{\game{0}(\pkeEve)}{0 \sample \pkeEve}
          - \probsample{\game{3}(\pkeEve)}{0 \sample \pkeEve}
        } \\
        &\leq \abs{
          \probsample{\game{0}(\pkeEve)}{0 \sample \pkeEve}
          - \probsample{\game{1}(\pkeEve)}{0 \sample \pkeEve}
        } \\
        &\quad + \abs{
          \probsample{\game{1}(\pkeEve)}{0 \sample \pkeEve}
          - \probsample{\game{2}(\pkeEve)}{0 \sample \pkeEve}
        } \\
        &\quad + \abs{
          \probsample{\game{2}(\pkeEve)}{0 \sample \pkeEve}
          - \probsample{\game{3}(\pkeEve)}{0 \sample \pkeEve}
        }\, .
      \end{align*}

      \noindent
      For the first game hop, recall that from the view of $\pkeEve$, $\game{0}$
        and $\game{1}$ are identical-until-bad. From this, we have
      \[
        \abs{
          \probsample{\game{0}(\pkeEve)}{0 \sample \pkeEve}
          - \probsample{\game{1}(\pkeEve)}{0 \sample \pkeEve}
        } \leq \probsample{\game{1}(\pkeEve)}{\bad}\, .
      \]
      %
      Next, note how in $\game{1}$, the DEM
        ciphertext $\demctxt$ is independent of the KEM ciphertext $\kemctxt$,
        meaning that the only way for $\pkeEve$ to learn whether $\demctxt$
        contains $\mssg_0$ or $\mssg_1$ is to study $\demctxt$ itself.
        However, the message has been encrypted with the one-time pad, using a
        value that is guaranteed to be uniformly random by the definition of
        a random oracle. Hence, the message is perfectly
        (i.e.\ information-theoretically) hidden from
        the view of $\pkeEve$, which implies that
      \[
        \abs{
          \probsample{\game{1}(\pkeEve)}{0 \sample \pkeEve}
          - \probsample{\game{2}(\pkeEve)}{0 \sample \pkeEve}
        } = 0\, .
      \]
      %
      Finally, $\game{2}$ and $\game{3}$ are again identical-until-bad:
        %Since this is technically a different bad event, let us call it $\bad^\prime$.
      \[
        \abs{
          \probsample{\game{2}(\pkeEve)}{0 \sample \pkeEve}
          - \probsample{\game{3}(\pkeEve)}{0 \sample \pkeEve}
        } \leq \probsample{\game{2}(\pkeEve)}{\bad}\, ,
      \]
      %
      giving us 
      \[
        \advantage{\indcpa}{\brescheme}[(\pkeEve)] 
          \leq \probsample{\game{1}(\pkeEve)}{\bad} + \probsample{\game{2}(\pkeEve)}{\bad}\, .
      \]

      If $\pkeEve$ has a significant chance of triggering the $\bad$ event, then
        this can be exploited by a reduction $\kemRed_0$ that simulates
        $\game{1}$ for $\pkeEve$, collecting candidate keys from random
        oracle queries, and outputting one of them uniformly at random at the
        end (together with the index indicating which challenge is being targeted).

        Let $\chalkeyi$ denote the symmetric key encapsulated in the $i$th
        challenge issued to $\kemRed_0$ (see \autoref{fig:ind-ow}).
        Then $\kemRed_0$ gains the following advantage:
      %
      \begin{align*}
        \advantage{\owcpa}{\kemscheme}[(\kemRed_0)] 
          &\coloneqq \probsample{(i, \demkey) \sample \kemRed_0}{\demkey = \chalkeyi}
        \intertext{
          Let us split the probability into the $\bad$ and $\neg\bad$ cases.
        }
        &= \probsample{(i, \demkey) \sample \kemRed_0}{\demkey = \chalkeyi \land \bad} 
          + \probsample{(i, \demkey) \sample \kemRed_0}{\demkey = \chalkeyi \land \neg\bad} \\

          In the case $\neg\bad$, none of the keys input to the random oracle
          were the solution to a challenge, and hence the latter probability
          evaluates to zero.
        }
        &= \prob{\bad} \cdot \condprobsample{(i, \demkey) \sample \kemRed_0}{\demkey = \chalkeyi}{\bad}
        \intertext{
          In the $\bad$ case, at least one of the calls to the random oracle was
          the solution to a challenge issued to $\kemRed_0$. Since $\pkeEve$
          makes at most $\qRO$ calls to the random oracle, the probability that
          $\kemRed$ outputs a correct solution is at least $\nicefrac{1}{\qRO}$:
        }
        &\geq \prob{\bad}\frac{1}{\qRO}\, , \\
        \implies &\probsample{\game{1}(\pkeEve)}{\bad} \leq \qRO \cdot
        \advantage{\owcpa}{\kemscheme}[(\kemRed_0)]\, .
      \end{align*}

      An analysis identical to the above gives that
      \[
        \probsample{\game{2}(\pkeEve)}{\bad} \leq \qRO \cdot
        \advantage{\owcpa}{\kemscheme}[(\kemRed_1)]\, ,
      \]
      giving us 
      \[
        \advantage{\indcpa}{\brescheme}[(\pkeEve)] 
          \leq \qRO \left( 
            \advantage{\owcpa}{\kemscheme}[(\kemRed_0)]
            + \advantage{\owcpa}{\kemscheme}[(\kemRed_1)]
          \right)\, .
      \]
      Finally, roll the two reductions ``into one'' by defining
      \[
        \advantage{\owcpa}{\kemscheme}[(\kemRed)] \coloneqq 
          \max \{
            \advantage{\owcpa}{\kemscheme}[(\kemRed_0)],
            \advantage{\owcpa}{\kemscheme}[(\kemRed_1)]
          \}\, ,
      \]
      which allows us to conclude that
      \begin{align*}
        \advantage{\indcpa}{\brescheme}[(\pkeEve)] 
          &\leq 
          \qRO \left( 
            \advantage{\owcpa}{\kemscheme}[(\kemRed_0)]
            + \advantage{\owcpa}{\kemscheme}[(\kemRed_1)]
          \right) \\
          &\leq 2\cdot\qRO\cdot\advantage{\owcpa}{\kemscheme}[(\kemRed)]\, .
      \end{align*}
      \qed
    \end{proof}

  \subsection{A Tight Reduction with Plaintext Checking}
    Inspecting the proof, it is clear that the main loss factor $\qRO$ comes
      from the reduction
      having to guess \emph{which} of at most $\qRO$ queries contains the
      symmetric key it is looking for. Fundamentally, this is because the reduction
      has no way of knowing whether a tuple $(\demkey, \ctxt)$ satisfies that
      $\ctxt$ encapsulates $\demkey$. If only $\kemRed$ could
      \emph{recognize} a correct solution when it saw one, then they could abort the game
      immediately upon receiving the correct key, which would happen if and only
      if the bad event would triggered in $\game 1$ and $\game 2$.

    One way to do this is to provide the reduction with a
      \emph{plaintext-checking oracle}, shown in \autoref{fig:pca}. This oracle
      takes a tuple $(\demkey, \ctxt)$ as input, and returns $\true$ if $\ctxt$
      encapsulates $\demkey$, and $\false$ otherwise. Crucially (and unlike
      the case of a CCA decryption oracle), there is no restriction on calling the
      oracle on challenges. We call the resulting security notion \emph{one-wayness
      under plaintext-checking attacks}, or $\owpca$.

    By the way, note how the lack of restrictions in the PCA oracle means that
      any game of indistinguishability would be trivially winnable in the
      presence of a plaintext-checking oracle. Hence, a security notion like
      $\ind\hy\pca$ would be \emph{void}, meaning unachievable, since there are
      always adversaries that trivially win.

          \pcreturn \kemdec_\sk(\ctxt) = \demkey

      The plaintext-checking oracle.

    \begin{theorem}\label{thm:bre-pca}
      Let $\kemscheme$ be a key encapsulation mechanism, let $\brescheme$ be the
      public-key encryption scheme defined in \autoref{fig:bre}, and let $\RO$ be a random oracle. 
      Then there is a SFBB reduction $\kemRed$ against $\kemscheme$ 
      for every adversary $\pkeEve$ against $\pkescheme$ satisfying
      \[
        \advantage{\indcpa}{\brescheme}[(\pkeEve^{\RO})]
        \leq 2\cdot \advantage{\owpca}{\kemscheme}[(\kemRed)]
      \]
      in the classical random oracle model. The runtime of $\kemRed$ is equal
      to that of $\pkeEve$, plus the overhead of simulating the random oracle. 
      If $\pkeEve$ makes $\qe$ calls to the challenge
      oracle, then $\kemRed$ makes $\qe$ calls to its own challenge oracle,
      and if $\pkeEve$ makes $\qRO$ calls to the random oracle, then $\kemRed$
      makes at most $\qRO$ calls to its plaintext-checking oracle.
    \end{theorem}

  \subsection{What Is a Quantum Random Oracle?}\label{sec:defs}
    A classical oracle for a function $f$ is a black-box procedure $\Oracle_f$
      such that, given input $x$, it returns $f(x)$ in such a way that no
      information about $f$, other than that which can be inferred from its
      output, is provided. It is helpful to think of the oracle as something that
      exists beyond your reach, ``in the sky'' so to speak, and with which you can
      only interact by sending inputs and receiving outputs.
      A random oracle, then, is simply a function oracle where the
      function $f$ was chosen uniformly at random from the space of all functions
      from $\bin^n$ to $\bin^m$.
  
    However, the operation $x \longrightarrow f(x)$ is generally not reversible,
      and therefore not \emph{unitary}, as is required of operations on quantum
      states. Therefore, we define \emph{quantum-accessible} function oracles to be
      oracles that apply the unitary $\unitary_f$, defined as the operation that
      takes computational basis states $\ket{x, y}$ to $\ket{x, y \xor
      f(x)}$. Generally, the state of the input may be entangled with whoever
      is performing the query, so saying that the oracle takes as input a quantum
      \emph{state}, e.g.\ $\sum_i \alpha_i \ket{x_i, y_i}$, would not be
      well-defined. Instead, we imagine that the query literally ships a
      collection of qubits over to the oracle, collected in the input and output
      registers $(\inputreg, \outputreg)$, and that the oracle then applies the
      $\unitary_f$ to the registers before shipping them back
      (see \autoref{fig:query} for an illustration).\footnote{
        If any of this terminology confuses you, then this would be a good time
        to have a read through the quantum primer found in \aref{sec:primer}!
      } 
  
    To see that this operation is unitary, it is enough to observe that it is
      \emph{reversible}: Making a query with the same registers a second time
      yields the original state, as seen by its effect on the computational basis
      states:
      \[ 
        \ket{x, y} \apply{\Oracle_f} \ket{x, y \xor f(x)}
          \apply{\Oracle_f} \ket{x, y \xor f(x) \xor f(x)} = \ket{x, y}\, .
      \]
  
    \noindent
    With this, we are ready to define quantum random oracles.
  
    \begin{definition}[Quantum Random Oracle]\label{def:qro}
      An $n$-bit-to-$m$-bit \emph{Quantum Random Oracle} (QRO), denoted $\RO$, is a
      quantum-accessible function oracle $\Oracle_f$ for a uniformly random
      function $f \in \funcspace{n}{m}$.
    \end{definition}
  
    \begin{remark} 
      Classical random oracles typically follow the standard for hash functions in
        being defined from the space of \emph{all} finite-length bit strings
        $\bin^*$ to the space of fixed-length bitstrings $\bin^m$. Technically, this means
        that $f$ not a function, but rather a a collection of random functions
        $f_\ell$, one for each input length $\ell$. However, since quantum random
        oracles must operate by unitary means, we will make life easier for
        ourselves by explicitly
        restricting the input domain of the random function to be $\bin^n$, and then just
        take for granted that any result trivially generalizes to
        collections of oracles with varying input length. 
  
      To see why this is the case, observe that, even when loading up a hash function on 
        real-world quantum hardware, the input \emph{length} to the hash function
        may not be placed in superposition, as this would not correspond to a
        well-defined unitary operation. Intuitively speaking, every ``branch'' in
        a superposition must be defined over the same number of qubits.
        Or in other words: Adding and removing qubits to an operation is a
        classical control mechanism, and not itself a quantum operation!
    \end{remark}

          \underline{\text{Adversary } \adv}\
                \<\< \underline{\text{Oracle } \Oracle_f} \\

          \outputreg \gets (\qubit_{j_1}, \ldots \qubit_{j_m}) 
            \<\sendmessageright*[\arrowlength]{\inputreg, \outputreg}
            \< \applyU{\unitary_f}{\inputreg, \outputreg} \\

  \subsection{Classical Oracles in a Quantum World}
    Sometimes, we want to provide a quantum algorithm with access to a
      classical oracle, but being unitary, we still face the issue of
      the operation $x \longrightarrow f(x)$ not being unitary. The way to fix,
      and make classical oracles quantum-compatible, is to simply define
      classical oracles to be quantum oracles that first measure the input
      register, collapsing it to some basis state $\ket{x}$. 

    \begin{definition}[Quantum-Compatible Classicle Oracle]
      A quantum-compatible classical oracle
        is a function oracle for $f$ that, on input qubit registers $(\inputreg, \outputreg)$,
        first performs the computational-basis measurement $\meas{}{\inputreg}$,
        and then performs the operation $\applyU{\unitary_f}{\inputreg,
        \outputreg}$, before returning the registers to the sender.
        Here, $f$ is the function defining the output of the classical oracle
        on input $x$, given any state and/or randomness internal to the oracle.
    \end{definition}

    \noindent
    Note that there is no need to collapse the output register $\outputreg$: If
      the input state is some superposition 
      $\sum_i \alpha_i \ket{x_i, y_i}$, then after measuring the $\inputreg$
      register, it will have collapsed to the state $\ket{x} \left( \sum_i
      \beta_i \ket{y_i} \right)$ for some $x$, and some set of amplitudes
      $\{\beta_i\}$. 
      Then the output state will be $\ket{x} \left( \sum_i \beta_i
      \ket{y_i \xor f(x)} \right)$. Observe that the function $f$ is still only
      evaluated on a single input, as desired.

    With this definition in hand, we will go on to ignore these implementation
      details and write classical oracles, such as those appearing in our
      security games, in terms of their classical input/output interface.

    Random oracles are typically treated as fully black-box, or ``monolithic'',
      meaning that we don't assume anything about their inner workings other
      than that it satisfies \autoref{def:qro}. Still, it is
      instructive to see how a quantum random oracle \emph{could} be
      implemented. Following are several possible implementations, which turn
      out to all be equivalent~\cite{C:Zhandry19}.

    \paragraph{Standard oracles.}
      This ``standard'' oracle, shown to the left in \autoref{fig:qros}, is the
        oracle that simply implements our
        intuition from the start of the section: It first 
        draws a function $f$ from $\bin^n$ to $\bin^m$ uniformly at random, storing
        the whol truth table as one exponential-sized list in the internal
        state $\state$, and thereafter operates as the quantum-accessible
        function oracle $\Oracle_f$.

    \paragraph{Phase oracles.}
      The ``phase'' oracle, shown in the middle of \autoref{fig:qros}, operates
        exactly like the standard oracle, except that it
        performs a phase operation on the output register rather than an xor.
        It therefore provides a different interface to the adversary, and
        is in that sense not equivalent in the sense of being
        indistinguishable, but \emph{are} easily reducible to each other, as
        one kind of oracle becomes identical to the other if you just apply the Hadamard
        transformation $\Hgate^{\otimes m}$ to the output register $\outputreg$
        before and after each query.

    \paragraph{Superposition oracles.}
      Instead of using a classically stochastic process to sample the random
        function at the outset, one can exploit the randomness inherent to
        quantum physics and simply provide a uniform superposition of
        \emph{all} functions from $\bin^n$ to $\bin^m$. This ``superposition''
        oracle, shown to the right in \autoref{fig:qros}, is just as
        (in)efficiently implemented, and is completely indistinguishable from a
        standard oracle from the point of view of the adversary. 

      The reason, in
        a nutshell, is that when applying the unitary $\unitary_h$, the oracle
        \emph{entangles} the adversary with the gigantic superposition that it
        keeps. Hiding away entanglement in this manner has the effect, from the
        ``local'' point of view of the adversary, of introducing randomness
        into the state of $\outputreg$. In technical terms, the state will no
        longer be ``pure'' (but rather ``mixed''), which could
        either be because of some hidden
        entanglement somewhere, or due to interference with a classically stochastic
        process---or both! However, there is no way to tell these cases apart
        without a full view of the combined system.

      Of course, with the choice of interface being orthogonal to the choice of
        sampling vs.\ superposition, there is also a ``superposition phase oracle''.
        We leave it to you to work out the details.

    \paragraph{Compressed oracles.}
      It turns out that there is a procedure through which we can efficiently
        implement a superposition oracle, as described above, in a manner
        completely analogous to the ubiquitous ``lazy-sampling'' technique for
        classical random oracles. Introduced by Zhandry~\cite{C:Zhandry19},
        these ``compressed oracles'' are enabled by the crucial insight that
        a uniform superposition over possible outputs will simply be
        represented by the all-zero string after a transformation to the
        Hadamard domain. Thus, we only have to store the output values for
        inputs that are \emph{not} in a uniform superposition, due to having
        been entangled to the adversary via a query, leading to an efficient
        simulation procedure.

      Of course, the above is an oversimplification: We still haven't said
        anything about how to deal with large superpositions over inputs, for
        example. To get there, and to see that what we end up with really is a
        faithful simulation, we will first need to lay some more groundwork. 
        \autoref{sec:compressed} is dedicated to this.
        
  \subsection{Domain-Separating Quantum Random Oracles}
    Sometimes, a construction uses more than one random oracle, which are
      then required to be independent. A standard way to solve this in practice
      is via \emph{domain-separation}~\cite{EC:BelDavGun20}: Given a random
      oracle $\RO$ from $\bin^{n+1}$ to $\bin^m$ (or a hash function like SHA3,
      if you are in the real world), let the random oracle $\RO[F]$ from
      $\bin^n$ to $\bin^m$ be defined as $\RO[F](x) \coloneqq \RO(0 \concat
      x)$, and likewise let the random oracle $\RO[G](x)$ be given by 
      $\RO[G](x) \coloneqq \RO(1 \concat x)$. Clearly, this works in the
      classical case, since the output of $\RO$ is uniformly random on each
      input, so flipping even a single bit makes the outputs completely
      uncorrelated. Further, it should be clear that the other direction also
      holds: You don't get anything \emph{more} with oracle access to
      $\RO$ directly than you do given oracle access to $\RO[F]$ and $\RO[G]$
      separately.

    But what about the quantum case? Now, we are supposed to be able to call
      the oracles in superposition, yet we can only call one oracle at a time.
      In particular, it seems that we can't make a query that is ``in a
      superposition of going to $\RO[F]$ and to $\RO[G]$'', even though this
      would be a trivial task given oracle access to $\RO$. Is it conceivable
      that we can do \emph{more} if we are given oracle access to $\RO$ instead?

    The following lemma answers this question in the negative: Domain-separation works
      just as well in the QROM as it does in the classical
      ROM---thankfully!\footnote{
        I'm grateful to Joseph Jaeger for showing me this reduction.
      }

    \begin{lemma}[Two Oracles $\cong$ One Oracle]\label{lemma:two-equals-one}
    Let $\RO[F]$ and $\RO[G]$ be quantum random oracles from $\bin^n$ to $\bin^m$,
      and let $\RO$ be a quantum random oracle from $\bin^{n+1}$ to $\bin^m$.
      %
      Then, for any adversary $\adv$ that expects simultaneous oracle access to 
        $\RO[F]$ and $\RO[G]$, there is a reduction $\bdv$ that, given oracle
        access to $\RO$, provides $\adv$ with a perfect simulation of $\RO[F]$
        and $\RO[G]$.

      And vice versa: For any adversary $\adv$ that expects oracle access
        to $\RO$, there is a reduction $\bdv$ that, given simultaneous access
        to $\RO[F]$ and $\RO[G]$, provides $\adv$ with a perfect simulation of $\RO[H]$.
    \end{lemma}

    \begin{proof}
      The first direction is trivial, and works exactly like the classical case: Whenever
        $\adv$ makes a call to $\RO[F]$ with registers
        $(\inputreg,\outputreg)$ , $\bdv$ makes an oracle call to $\RO$
        with registers $(\qubit \concat \inputreg, \outputreg)$, 
        where $\qubit$ is a qubit placed in the state $\ket{\qubit} = \ket 0$; and likewise
        for calls to $\RO[G]$, except with $\ket \qubit$ set to $\ket 1$. The
        registers $(\inputreg,\outputreg)$ are then returned to $\adv$ as usual.

      For the other direction, let the controlled swap gate $\CSWAPgate$ be
        defined by the following operation on computational basis states
        (where $\abs{x} = \abs{z}$):
      \[
        \ket{0}\ket{x}\ket{z} \apply{\CSWAPgate} \ket{0}\ket{x}\ket{z}\, , \quad
        \ket{1}\ket{x}\ket{z} \apply{\CSWAPgate} \ket{0}\ket{z}\ket{x}\, .
      \]

      \noindent
      The reduction $\bdv$ sets up up a new $n$-qubit register
        $\register[Z]$, initialized to the uniform superposition over all
        $z \in \bin^n$. Then, on input a query to $\RO$ with the registers $(q
        \concat \inputreg, \outputreg)$, $\bdv$ does the following: 
        \begin{enumerate}
          \item Apply $\CSWAPgate$ on $\inputreg$ and $\register[Z]$, with qubit
            $\qubit$ as the control;
          \item Send $(\inputreg, \outputreg)$ to $\Oracle[F]$, and
            $(\register[Z], \outputreg)$ to $\Oracle[G]$;
          \item Apply $\CSWAPgate$ a second time to the same registers;
          \item Return $(\inputreg, \outputreg)$ to $\adv$. 
        \end{enumerate}

      \noindent
      To see that this leads to the correct distribution, consider the
        result of applying this procedure to the first query if
        qubit $\qubit$ is in some superposition state $\ket q = \alpha \ket 0 +
        \beta \ket 1$, and $\inputreg$ and
        $\outputreg$ are set to the computational basis states
        $\ket{x}_\inputreg \ket{y}_\outputreg$. Then we start out with the
        combined state
      \begin{align*}
        &\left( \alpha \ket{0}_\qubit + \beta \ket{1}_\qubit \right) \ket{x}_{\inputreg} \ket{y}_{\outputreg} \left(
        \sum_{\forall z \in \bin^n} \frac{1}{\sqrt{2^n}} \ket{z}_{\register[Z]} \right) \\
        &\qquad = \frac{1}{\sqrt{2^n}} \sum_{\forall z \in \bin^n} \alpha \ket{0}_\qubit
          \ket{x}_{\inputreg} \ket{y}_{\outputreg} \ket{z}_{\register[Z]} +
          \beta \ket{1}_\qubit \ket{x}_{\inputreg} \ket{y}_{\outputreg} 
          \ket{z}_{\register[Z]}\, . 
        \intertext{
          After applying the first $\CSWAPgate$, we get the state
        }
        &\quad \apply{1.} \quad 
        \frac{1}{\sqrt{2^n}} \sum_{\forall z \in \bin^n} 
          \left( \alpha \ket{0}_\qubit
          \ket{x}_{\inputreg} \ket{y}_{\outputreg} \ket{z}_{\register[Z]} +
          \beta \ket{1}_\qubit \ket{z}_{\inputreg} \ket{y}_{\outputreg} 
          \ket{x}_{\register[Z]} \right)\, . 
        \intertext{
          At this point, the registers $(\inputreg, \outputreg)$ are sent to
          $\RO[F]$, and then registers $(\register[Z], \outputreg)$ are sent to
          $\RO[G]$, with the resulting state
        }
        &\quad \apply{2.} \quad 
        \frac{1}{\sqrt{2^n}} \sum_{\forall z \in \bin^n}
          \left( \alpha \ket{0}_\qubit
          \ket{x}_{\inputreg} \ket{y \xor \RO[F](x) \xor \RO[G](z)}_{\outputreg} \ket{z}_{\register[Z]} +
          \beta \ket{1}_\qubit \ket{z}_{\inputreg} \ket{y \xor \RO[F](z) \xor \RO[G](x)}_{\outputreg} 
          \ket{x}_{\register[Z]} \right)\, . 
        \intertext{
          Applying $\CSWAPgate$ a second time gives us
        }
        &\quad \apply{3.} \quad 
        \frac{1}{\sqrt{2^n}} \sum_{\forall z \in \bin^n}
          \left( \alpha \ket{0}_\qubit \ket{x}_{\inputreg} \ket{y \xor
          \RO[F](x) \xor \RO[G](z)}_{\outputreg} \ket{z}_{\register[Z]} +
          \beta \ket{1}_\qubit \ket{x}_{\inputreg} \ket{y \xor \RO[F](z) \xor \RO[G](x)}_{\outputreg} 
          \ket{z}_{\register[Z]} \right)\, ,
      \end{align*}

      \noindent
      at which point the registers $\inputreg$ and $\outputreg$ are returned to $\adv$.  

      Note that register $\outputreg$ ends up entangled with register $\register[Z]$. As
        explained when discussing superposition oracles, hidden entanglement
        inuces a classical probability distribution when it is hidden from view, and
        maximal entanglement with a hidden uniform superposition is
        indistinguishable from the uniform probability distribution. Since the values of
        $\RO[F]$ and $\RO[G]$ are xored into the output state, this uniformity
        carries over; and yet, again thanks to entanglement, we see that we are
        guaranteed consistency upon repeat queries. 

      Since the correct behaviour is exhibited on all input basis states
        $\ket{b \concat x, y}$, thanks to the linearity of quantum mechanics,
        we may conclude that the simulation exhibits the correct behaviour on
        all input states.
      \qed
    \end{proof}
