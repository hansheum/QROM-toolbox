\section{The Random Oracle Model}\label{sec:rom}
  This chapter introduces the concept of the random oracle. Then, we
    introduce the \U-transform, which is the second half of the Fujisaki--Okamoto
    transformation, and, as a first application of the random oracle model,
    prove that if we have a deterministic PKE scheme
    that achieves one-way security, taking it through the \U-transform gives us
    a KEM that achieves indistinguishability. This proof will teach us several useful
    tricks, foreshadowing the QROM tools that will be introduced in \cref{sec:o2h}.

  \subsection{Modelling Hash Functions as Random}
    As explained in \cref{sec:basics:primitives}, a hash function is 
      a deterministic algorithm that takes arbitrary-length inputs and produces
      a fixed-length ``fingerprint'' of that input, such that re-evaluating the hash function on
      the same input produces the same fingerprint. 
      
    But is a hash function really a \emph{function}? Well, since hash functions can take arbitrary-length
      inputs, they can at least not be \emph{finite-domain} functions. Still, it is
      helpful to think of hash functions as an infinite \emph{collection} of
      finite-domain functions $\{f_n\}$, with one $f_n$ for each possible input length $n$. 
      Let us for the sake of simplicity specialize to one such $f_n$.
      If the hash function produces fingerprints of (fixed) length $m$, then
      this is a function from the set $\bin^n$ to $\bin^m$, which is much
      simpler to reason about. If needed, we can then always go back to the full
      picture by considering the collection $\{f_n\}$ instead.

    We mentioned that cryptographic hash function should produce
      random-looking fingerprints, and that it should further be hard
      to find two inputs with the same fingerprint,
      even though such collisions will definitely \emph{exist} whenever $n$ is
      larger than $m$ (which it usually is), by the pigeonhole principle.

    Indeed, in typical applications there must be a huge number of collisions.
      Consider the case of hashing a 10MB picture: then $n$ is $80$ million (since there are
      $8$ bits in a byte), whereas a typical choice for the output length $m$
      might be $256$. 
      This leads to a truly astronomical number of colliding input values: the pigeonhole
      principle tells us that at least one of the hash function's $2^m$ possible
      output values will map to at least 
      \[
        \frac{2^n}{2^m} = \frac{2^{80{,}000{,}000}}{2^{256}} = 2^{79{,}999{,}744}
      \]
      different input values. For comparison, the
      number of atoms in the observable universe is estimated to be
      around $10^{80} \approx 2^{266}$.

    And yet, actually \emph{finding} even a single such collision can be very
      hard. To see this, assume that the hash function is a function
      $f$ drawn uniformly at random from the set of all functions from $\bin^n$ to
      $\bin^m$; since $f$ is uniform, we are guaranteed that there is no
      internal structure that can be exploited to find collisions, and no
      special inputs that have an a priori
      higher probability of being part of a collision than others. 
      Hence, an attacker has no choice but to
      evaluate the function on different inputs until it finds two colliding
      outputs. 

    How many times will the attacker have to evaluate $f$ before it is expected
      to find a collision?
      Let us calculate. First, let $\bool{f(x_1) = f(x_2)}$ be the predicate that
      takes the value $1$ if $f(x_1) = f(x_2)$, and $0$ otherwise.
      Let $x_1$ and $x_2$ two arbitrary but distinct input values.
      Since there are $2^m$ possible outputs, and each input were assigned an
      output uniformly at random (that's what it means to draw a function at random), 
      the probability that $\bool{f(x_1) = f(x_2)} = 1$
      is exactly $2^{-m}$. Hence, for any choice of distinct $x_i$ and $x_j$, 
      the expectation value is also
      \[
        \expect{\bool{f(x_i) = f(x_j)}} = 2^{-m}\, ,
      \]
      with the expectation taken over the choice of $f$.

    Now, let $\collisions_q$ be the expected number of
      collisions observed after $q$ evaluations of $f$ on different inputs.
      \[
        \collisions_q = \expect{\sum_{i = 1}^{q-1} \sum_{j = i+1}^q\, \bool{f(x_i) = f(x_j)}}\, .
      \]
      Here, the sum is taken over $j > i$ to avoid double-counting the pairs. A useful
      fact about expectation values is
      that, unlike (correlated) probabilities, they are linear; this may
      therefore be written
      \[
        \collisions_q 
          = \sum_{i = 1}^{q-1} \sum_{j = i+1}^q
            \expect{\bool{f(x_i) = f(x_j)}} 
          = \sum_{i = 1}^{q-1} \sum_{j = i+1}^q \frac{1}{2^m} 
          = \frac{q(q-1)}{2} \cdot \frac{1}{2^m} 
          \approx \frac{q^2}{2^{m+1}}\, .
      \]
      We wanted to know how large $q$ must be for $\collisions_q \approx 1$.
      With an explicit formula in hand, we can find our answer by solving for
      $q$, then inserting $m = 256$:
      \[
        \collisions_q \approx 1 
        \Longleftrightarrow q \approx \sqrt{2^{m+1}} 
        \Longleftrightarrow q \approx \sqrt{2^{257}} \approx 2^{128}\, .
      \]
      So despite the astronomical number of collisions, we would still 
      have to evaluate a random function with length-$256$ outputs on roughly
      $2^{128}$ input values before we would expect to ever find one.
      This is comfortably beyond the capabilities of even the largest
      supercomputers.

    Incidentally, the somewhat unintuitive fact that the expected number of
      collisions grows as the \emph{square} of the number of
      potentially-colliding items
      is sometimes known as the ``birthday paradox'', so named because 
      of the surprising fact that, assuming everyone are assigned birthdays at
      random, it only takes a room of $23$ people before the
      probability that two of them shares a birthday exceeds $50\%$.
      
  \subsection{Monolithic Random Oracles}
    The idealization that we just did when we studied a uniformly random function
      as a placeholder for a hash function, turned out to be very useful in
      analyzing the effort required to find a collision: the no-structure
      guarantee is what enabled us to explicitly calculate how many evaluations
      one would expect to need to find one.

    However, this same no-structure guarantee also means that there is no way
      to actually \emph{store} $f$ more efficiently than to simply keep a
      truth table with all the input
      and output values. For a function from $n$ to $m$ bits, one such
      input-output pair will take up $n+m$ bits of memory, and there will be
      one such pairs for every possible input, so that the total memory
      requirement for storing $f$ is $2^n \cdot (n+m)$. If the input length $n$
      is greater than $40$, this would already be in the terabytes range, and
      $n$ greater than $60$ is
      beyond the capabilities of even the world's largest supercomputers.

    As we will see, hash function are very useful primitives when building
      cryptography. However, we need our cryptography to be
      \emph{efficiently implementable}. This means that we can't just
      put in a to be truly random $f$ and expect that systems would actually be
      able to run it. Indeed, even just assuming that the hash function behaves
      like a random function for the sake of the security proof does not work,
      since we also need to be able to argue that any hypothetical attackers 
      are themselves efficient (otherwise they could just break all our crypto via
      brute-force search).
      %guaranteed to be efficient, meaning they do not have access to
      %exponentially large resources like time and memory.
      If we assume the hash function uniform, an efficient attacker would not even be able to
      \emph{run} our algorithms, much less break them.

    A common solution in theoretical computer science is to instead provide
      evaluations of the inefficient function as an \emph{oracle}. Imagine a giant computer
      that lives in the sky, which is given as much resources as it needs to store
      and evaluate random functions. Everyone in the world are given
      input/output access to this \emph{random oracle}, so that they can evaluate $f$ by sending
      $x$ to the oracle and receiving $f(x)$ in return.
      Crucially, given the same input $x$, everyone will see the same value for
      $f(x)$, which means that the random oracle can be used in place of 
      a publicly known hash function such as SHA3.

    The inner workings of such an oracle is shown in pseudocode in
      \cref{fig:lazy-sampling} (left): the
      ``Initialize'' method initialzes our random oracle $\RO$ by sampling $f$
      uniformly at random from the set of all functions from $n$ to $m$ bits.
      Thereafter, the ``Oracle'' interface takes inputs $x$ and returns $f(x)$.

    Note how $\RO$ is implicitly taken to be \emph{stateful}, in the sense
      that it has a persistent memory that stores $f$ after initialization.

  \subsection{Simulation via Lazy-Sampling}\label{sec:lazy-sampling}
    The statefulness of $\RO$ opens up for a very simple and efficient way to
      \emph{simulate} a random function, known as lazy-sampling. The idea is
      simple: start with an empty function table; then, every time you receive an input $x$, check if
      your table already defines an output value for $x$; 
      if so, return that value, and otherwise draw an output
      value uniformly at random and store it together with $x$. The result is an
      oracle that behaves identically to a monolithic random oracle, i.e.\ to a
      uniformly random function. And yet, if this ``lazy-sampled'' random oracle
      receives at most $q$ queries, then at most $q \cdot (n+m)$ bits is required to
      store the table -- an exponential improvement over the memory requirements
      of the monolithic oracle.

    The lazy-sampling procedure is shown in pseudocode in
      \cref{fig:lazy-sampling} (right): First, the database $\Db$ is initialized
      with an empty tuple (recall that databases are lists of tuples); then the
      oracle interface, on input $x$, checks if $\Db$ already contains $x$, and
      if not, samples uniformly from the set of output strings $\bin^m$ and
      stores it in $\Db[x]$.

  \subsection{From One-wayness to Indistinguishability: The $\U$-transform}
    The Fujisaki-Okamoto transformation~\cite{C:FujOka99} is a recipe for
      constructing a strongly-secure key-encapsulation mechanism from a
      weakly-secure public-key encryption scheme. It is used as part of many
      post-quantum KEMs, including the now-standardized ML-KEM (Kyber)~\cite{FIPS203}. 

    The transformation can be seen as a composition of two sub-transformations, 
      which are referred to in the literature as the \T- and
      \U-transformations.~\cite{TCC:HofHovKil17}.
      %, as defined by Hofheinz et al. (hereafter HHK). 
      Given a probabilistic PKE scheme, the first transformation
      (\T) de-randomizes it by first deriving the random coins by hashing
      the message (and possibly the public key), then running the encryption
      algorithm using those coins; then, after decrypting, it re-derives the
      random coins and re-encrypts the message to verify that resulting
      ciphertext matches the input. (For more details on the \T-transform, see
      App.~\ref{sec:ttransform}.)

    The second transformation (\U) then 
      builds a KEM from a deterministic PKE like the above by sampling a random
      message, encrypting it, and hashing it 
      (possibly together with the public key and ciphertext) to derive a
      symmetric key $\eK$. This is the transformation that will serve as our
      running example.\footnote{
        When Hofheinz et al.~\cite{TCC:HofHovKil17} first defined
        the \T- and \U-transforms, they actually defined several \U-variants;
        %that differ from the variant discussed here
    		%in how they handle invalid ciphertexts and in what they hash into the
        %output key; 
        \cref{def:U-transform} corresponds to
        \UExpMess in their notation (message-only hashes, explicit decryption failures).
      }

    As explained in \cref{sec:basics}, One-way security under Chosen
      Plaintext Attacks, or \owcpa, is really a minimal security
      requirement for PKE schemes, and should be considered too weak a security
      goal for most use-cases. 
      %The goal of One-Wayness (OW) simply says that
      %given a ciphertext, it should be hard to recover the plaintext, and the
      %power of Chosen Plaintext Attacks (CPA), the ability to encrypt any
      %message under the key you are targetting, are of course ever-present when
      %encryption is public.
      Much preferred would be the stronger security requirement of
      \emph{indistinguishability} under chosen-plaintext attacks, or
      \indcpa.\footnote{
        The standard security requirement for deployable KEMs is an even stronger one,
        namely indistinguishability under chosen-\emph{ciphertext} attacks, or
        \indcca. 
        As it turns out, the \U-transform also achieves this, provided the
        re-encryption check from the \T-transform is carried forward; this will
        be covered in later chapters (to appear).
      } 

    However, stronger security assumptions usually mean less efficient
      schemes, as the parameters must be increased to compensate for the
      increased attack surface. What's worse, we are taking as our starting
      point a \emph{deterministic} encryption scheme. Such a PKE scheme could
      \emph{never} achieve indistinguishability, since the adversary can simply
      re-encrypt the two candidate messages, and check which of them
      encrypts to the challenge ciphertext.

    Despite this, taking our deterministic PKE scheme through the \U-transform
      will in fact give us a KEM that \emph{does} achieve indistinguishability
      \ldots and the object that allows us to cross that chasm
      %between one-wayness and indistinguishability 
      is precisely the \emph{random oracle}.

    The strategy of the security reduction will rely on the fact that it can
      fully control the random oracle for the adversary, inspecting its queries
      and answering them via the lazy-sampling procedure from \cref{sec:lazy-sampling}. 
      Intuitively speaking, in order to successfully distinguish, the adversary
      will have to have called the random oracle on one of
      the messages used to derive the ephemeral key. 
      The reduction can recognize this the moment it happens, by re-encrypting
      each message and checking if the encryption matches the challenge it was
      issued; if so, it wins at the one-wayness game by outputting that message.

      %able to recognize the correct solution; this fact allows us to get
      %a tight bound in this case. (Otherwise we would have to guess which of the
      %calls to the random oracle contained the solution we are looking for,
      %which would incur a tightness loss related to the probability that
      %we guess correctly.)

    To summarize, if $\dPKE$ satisfies one-wayness
      (\cref{def:owcpa}), then $\KEM$ satisfies indistinguishability
      (\cref{def:indcca}), as captured in the following theorem.

    \begin{theorem}[\dPKE is \owcpa $\To$ \KEM is \indcpa]
      \label{thm:cparom}
      Let \dPKE be a deterministic PKE scheme, let \RO be a random oracle, 
      and let the $\KEM = \U[\dPKE, \RO]$.
      Then there is a simple, fully black-box reduction $\bdv$, such that for
      every adversary $\adv$,
      %that makes at most $\qe$ calls to the challenge oracle, 
      \[
        \advantage{\indcpa}{\KEM} \leq \advantage{\owcpa}{\dPKE}[(\bdv^{\adv})]\, .
        %+ \frac{\qe}{2^m}\, .
      \]
      The adversary $\bdv$ runs in the same time as $\adv$, plus the %(relatively small) 
      overhead of lazy-sampling a random oracle.
    \end{theorem}

      The four games are given in pseudocode in \cref{fig:cparom-hops}, in a
        layout matching \cref{fig:cparom-hops-illustrated}, and with
        changes between games highlighted.
        To make the argument formal, start by recalling the definition of a
        distinguishing advantage; we will use the ``difference'' version of
        distinguishing advantages, as
        it fits more cleanly with this ``game hopping'' style of proof.
        \[
        	\advantage{\indcpa}{\KEM} \coloneqq \abs{
        		\condprobsample{
        			\experiment{\indcpa}{\KEM}
        		}{1 \gets \adv}{\chalbit = 0}
        		- \condprobsample{
        			\experiment{\indcpa}{\KEM}
        		}{1 \gets \adv}{\chalbit = 1}
        	}\, .
        \]
        The game $\game 1$ is just the real-world ($\chalbit=0$) $\indcpa$ game, with the
        construction of \KEM written out explicitly, together with a lazy-sampled
        random oracle. Similarly, $\game 4$ is just the random-world
        ($\chalbit=1$) $\indcpa$ game with the \KEM construction explicit. We
        can therefore write
        \[
        	\advantage{\indcpa}{\KEM} = \abs{
        		\probsample{ \game{1}(\adv) }{1 \gets \adv}
        		- \probsample{ \game{4}(\adv) }{1 \gets \adv}
        	}\, .
        \]
        We are of course always free to ``add zero'' by adding and subtracting
        the same term, so this is equal to:
        \begin{align*}
          \advantage{\indcpa}{\KEM} &= |\probsample{ \game{1}(\adv) }{1 \gets \adv} \\
            &\qquad - \probsample{ \game{2}(\adv) }{1 \gets \adv} + \probsample{ \game{2}(\adv) }{1 \gets \adv} \\
            &\qquad - \probsample{ \game{3}(\adv) }{1 \gets \adv} + \probsample{ \game{3}(\adv) }{1 \gets \adv} \\
            &\qquad - \probsample{ \game{4}(\adv) }{1 \gets \adv}|\, .
        \end{align*}
        Applying the triangle inequality then gives us an upper-bound 
          on the original distinguishing advantage as the sum of the distinguishing
          advantages between successive games:
        \begin{align*}
          \advantage{\indcpa}{\KEM} &\leq 
            \abs{\probsample{ \game{1}(\adv) }{1 \gets \adv} 
              - \probsample{ \game{2}(\adv) }{1 \gets \adv}} \\
            &\qquad + \abs{\probsample{ \game{2}(\adv) }{1 \gets \adv} 
              - \probsample{ \game{3}(\adv) }{1 \gets \adv}} \\
            &\qquad + \abs{\probsample{ \game{3}(\adv) }{1 \gets \adv}
              - \probsample{ \game{4}(\adv) }{1 \gets \adv}}\, .
        \end{align*}

        Let us analyze each distinguishing advantage in turn.
          First, $\game 1$ delays defining \ldots

        \hhnote{cont}

          the only difference between $\game 1$ and $\game 2$ is 
          introduction of the flag $\bad$; this flag does not otherwise affect the
          behaviour of the game, and it is therefore completely hidden from
          $\adv$'s view. As a result, the first difference evaluates to $0$. 
          %Since the same is true for $\game 3$ vs.\ $\game 4$, we actually have:
        \begin{align*}
          \abs{\probsample{ \game{1}(\adv) }{1 \gets \adv} 
            - \probsample{ \game{2}(\adv) }{1 \gets \adv}} = 0\, . 
        \end{align*}
        Let us use the law of total probability (and the triangle inequality
        again) to split into two distinguishing advantages, one for
        the case that $\bad$ is set to $\true$ and one for the case that $\bad$
        remains $\false$.
        \begin{align*}
          \advantage{\indcpa}{\KEM} &\leq 
            \abs{ \probsample{ \game{2}(\adv) }{1 \gets \adv \land \neg \bad} 
              - \probsample{ \game{3}(\adv) }{1 \gets \adv \land \neg \bad}} \\
            &\qquad + \abs{ \probsample{ \game{2}(\adv) }{1 \gets \adv \land \bad} 
              - \probsample{ \game{3}(\adv) }{1 \gets \adv \land \bad}}\, .
        \end{align*}
        These distinguishing advantages represent the probability that the adversary notices
        that we are exchanging the real key for a random key. Notice that
        $\dPKE$ being deterministic and correct imposes a one-to-one
        correspondence between messages and ciphertexts. This means that if $\bad$ 
        is never set to $\true$, then re-encryption never yielded $\chalctxt$,
        which in turn implies that the random oracle was never called on $x^*$. 
        Thanks to the uniform nature of random oracles, this means that 
        both real and random $\eK^*$ will look completely random from the
        point of view of $\adv$. Hence, the two probabilities 
        $\probsample{ \game{2}(\adv) }{1 \gets \adv \land \neg \bad}$
        and
        $\probsample{ \game{3}(\adv) }{1 \gets \adv \land \neg \bad}$
        are equal, and the $\neg \bad$ part of the distinguishing advantage is
        zero:
        \begin{align*}
          \advantage{\indcpa}{\KEM} &\leq 
            \abs{ \probsample{ \game{2}(\adv) }{1 \gets \adv \land \bad} 
              - \probsample{ \game{3}(\adv) }{1 \gets \adv \land \bad}}\, . 
        \end{align*}
        We have reached the crux of the matter: The distinguishing
        advantage of $\adv$ can be characterized as the difference in its
        probability of outputting $1$ \emph{and} in calling the random oracle on
        the correct $x^*$. But notice that 1) up until the point that $\bad$ is set to
        $\true$, $\eK^*$ will look completely random to $\adv$, and 2) \emph{after}
        $\bad$ is set to $\true$, an adversary would easily be able to
        distinguish, e.g.\ by using $\dPKE$ to
        re-encrypt $x^*$ and confirm that it gives the correct
        $\chalctxt$, then comparing $\eK^*$ against $\RO(x^*)$.
        We therefore lose nothing of significance if we simply bound this
        distinguishing advantage by the probability that $\bad$ is set to $\true$.
        \begin{align*}
          \advantage{\indcpa}{\KEM} &\leq 
            \probsample{ \game{2}(\adv) }{\bad} 
              = \probsample{ \game{3}(\adv) }{\bad}\, ,
        \end{align*}
        where, again, the latter equality holds due to the view of $\adv$ being equal
        in both games up until the point that $\bad$ is set to $\true$, since
        random oracles are perfectly preimage-hiding.

      We now have a bound in terms of $\game 3$ only, which is a game that a
        one-wayness adversary $\bdv$ can simulate while injecting its own
        challenge ciphertext into the simulation. 
        Further, the $\bad$ flag was chosen in such a way that the case that
        $\bad$ is set to $\true$ corresponds exactly to the case that $\bdv$
        finds the challenge message $x^*$ required to win the one-wayness game.
        Since the quantifiers in the theorem statement only requires that for
        every $\adv$, there \emph{exists} a $\bdv$ that achieves the stated
        bound, we are free to construct such a $\bdv$ explicitly;
        one solution is shown in pseudocode in \cref{fig:cparom-red}.

      To summarize: \emph{Either} $\adv$ never calls the
        random oracle on the correct $x^*$ ($\bad = \false$), 
        in which case the view of $\adv$ is
        perfectly consistent with being in the real-world game, \emph{or else} it
        called $\RO$ on $x^*$ ($\bad = \true$), in which case our constructed
        adversary $\bdv$ given in \cref{fig:cparom-red} wins at the one-wayness
        game. This allows us to conclude that, regardless of the attack strategy
        employed by the given adversary $\adv$, our constructed adversary $\bdv$
        wins the one-wayness game with advantage
      \[
        \advantage{\owcpa}{\dPKE}[(\bdv)] =
          \probsample{\game{3}(\adv)}{\bad}\, ,
      \]
      so that
      \[
        \advantage{\indcpa}{\KEM} \leq 
        \advantage{\owcpa}{\dPKE}[(\bdv)]\, . 
      \]
      \qed
    \end{proof}

        \begin{lemma}[Classical O2H, Find]\label{thm:co2h-find}
          let $\RO: \bin^n \to \bin^m$ be a random
          oracle, and let $z$ be a bitstring that depends arbitrarily on $\RO$.
          Let $\solset \subseteq \bin^n$ be a subset of inputs, and let $\RO

          $\bot$. Then for every distinguisher $\distinguisher$,
          \[
              \abs{\prob{1 \sample \distinguisher^{\ro}(z)}
                  - \prob{1 \sample \distinguisher^{\ro\backslash \solset}(z)}}
                = \probsample{\distinguisher^{\ro \backslash \solset}(z)}{\find}\, .
          \]
        \end{lemma}

      %\todoenum[Provide explanations of:]{

      For our security proofs, we will be working in the game-hopping
        paradigm of Shoup~\cite{EPRINT:Shoup04}.
        The fundamental lemma of game hopping states that the distinguishing advantage
        of an adversary can be bounded in terms of their distinguishing advantage
        over several intermediary game ``hops''.

      \begin{lemma}[Fundamental Lemma of Game Hopping]\label{lemma:game-hopping}
        For any adversary $\adv$ tasked with distinguishing $\game{0}$ from
        $\game{n}$, and for any games $\game{1}, \ldots \game{n-1}$,
        there exist adversaries $(\adv_1, \ldots, \adv_n)$ such that
        \[
          \abs{
            \probsample{\game{0}(\adv)}{1 \sample \adv} -
            \probsample{\game{n}(\adv)}{1 \sample \adv}
          } \leq \sum_{i = 1}^n \abs{
            \probsample{\game{i-1}(\adv)}{1 \sample \adv_i} -
            \probsample{\game{i}(\adv)}{1 \sample \adv_i}
          }\, .
        \]
      \end{lemma}

      \noindent
      The lemma states that, if $\adv$ were able to distinguish, then
        at least one of $\adv_1, \ldots, \adv_n$ must be able to
        distinguish too---and vice versa, that if none of the $\adv_i$ are able to
        distinguish, then neither is $\adv$.
        (In fact, the $\adv_i$ that achieve this will in essence be just copies
        of $\adv$.)

      The proof is remarkably simple, reproduced here for those who haven't
        seen it.

      \begin{proof}
        For all $i$ from $1$ to $n-1$, insert $0 = \probsample{\game{i}(\adv_i)}{1 \sample \adv_i} -
        \probsample{\game{i}(\adv_i)}{1 \sample \adv_i}$ into the absolute value
        on the left hand side, then apply the union bound.
        \qed
      \end{proof}
