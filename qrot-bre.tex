  Let us begin by introducing our motivating public-key encryption scheme $\brescheme$, which will follow us
    throughout as we explore the world of O2H lemmas. It is a hybrid public-key
    encryption scheme, meaning that it is built from a Key Encapsulation Mechanism (KEM) and a
    Data Encapsulation Mechanism (DEM). Two differences from the canonical
    hybrid encryption construction: First, the symmetric key is not used as-is,
    but rather derived by hashing the key output by the KEM; in the literature
    on the Fujisaki-Okamoto transformation~\cite{C:FujOka99} this step is known as
    the ``U transform''~\cite{TCC:HofHovKil17}. Secondly, the
    DEM is taken to be the One-Time Pad (OTP).\footnote{
      Information-theoretical DEM security
      is not actually required for the proofs to go through, 
      but it serves well as an example scheme, as using the OTP significantly
      simplifies our analysis.
    } 

  The algorithms of $\pkescheme$ are shown in \autoref{fig:bre}. The public parameter
    generation algorithm $\pkpm$ and the keypair generation algorithm $\pkkg$
    are inherited as-is from the underlying KEM, while the encryption algorithm
    $\pkenc$ and the decryption algorithm $\pkdec$ are as outlined above: When
    encrypting, the symmetric key $\demkey$ is used as a seed to the random
    oracle $\RO$, yielding a random string $\rnd$, which is then used as a
    one-time pad key, encrypting the message $\mssg$ by xoring with $\rnd$. For
    decryption, $\rnd$ is re-computed and the xor operation is repeated, revealing
    $\mssg$.

  The scheme 
    %and its CCA-secure variants (where CCA security is usually achieved by adding
    %a MAC to the encryption process, which is then verified during decryption), 
    was first analyzed by Bellare and
    Rogaway in their seminal paper ``Random Oracles are
    Practical''~\cite{CCS:BelRog93},\footnote{
      If you still haven't read Bellare and Rogaway's masterful introduction of
      random oracles to provable security, do so now! Go on, I'll wait.
    } and has shown up in many contexts since,
    including as the REACT transform~\cite{RSA:OkaPoi01}, as non-committing
    encryption~\cite{C:Nielsen02a,CSF:CLNS17}, to achieve security against
    selective-opening attacks~\cite{PKC:HJKS15,AC:LYHW21}, and 
    against mass surveillance~\cite{PKC:BruHeuSta24}. We refer to it as
    Bellare-Rogaway Encryption (BRE).\footnote{
      Technically, BRE is not \emph a scheme, but rather a class of schemes or
      a construction \emph{paradigm}, in much the same way that ``hybrid encryption'' is.
      This is mainly due to the multiple ways in which CCA security can be achieved,
      for example through an encrypt-then-mac construction. 
    }

  At first glance, the hashing of the symmetric key may seem completely
    unnecessary: Presumably, the symmetric key $\demkey$ output by the KEM already has
    high enough entropy, such that hashing it only has the effect of changing
    it from one random value to another. However, forcing the key to go through
    the random oracle will allow our reduction to learn the value of the key,
    which will allow us to weaken the assumed security of our underlying KEM, 
    from indistinguishability to merely one-wayness. 

  \subsubsection{Preliminaries.}
    Let us define a few conventions. First, whenever a value is generated
      dependent on some other public value, such as the public key $\pk$ being
      dependent on the public parameters $\params$, which in turn depend on the
      security parameter $\secpar$, we assume without loss of generality that
      the derivative value includes descriptions of the prior values (so if you
      know $\pk$, then you also know $\params$, and so on). Further, we assume
      that if a secret key $\sk$ belongs to the keypair $(\pk, \sk)$, then it
      also includes a description of $\pk$. This is without loss in the sense
      that after key generation, one could always define the keypair to be
      $(\pk, (\pk, \sk))$; though note that doing this enforces a
      unique-public-key relation, since now each private key will correspond to
      exactly one public key. (There exist schemes that violate this, and
      relaxing this relation may be beneficial to certain security
      proofs~\cite{EC:BelHofYil09}.)

    Adversaries $\adv$ are assumed to be generally quantum agents, having
      access to as much classical and quantum memory as they need, on which
      they can apply unitary operations and measurements as they
      please. (We will come upon cases later where restricting this
      assumption will be of benefit us, but for now we stick to the general
      case.) We will mostly think of these agents as being \emph{efficient} in the sense of
      running in time polynomial in the security parameter $\secpar$, although
      we prefer the concrete treatment of security wherein asymptotics are
      avoided, and the running time of reductions are instead stated directly in terms
      of the running time of the original adversary. We may also
      consider \emph{unbounded} adversaries; these can be thought of as running
      in time (and space) exponential in the security parameter.

    If the adversary $\adv$ has access to the random oracle $\RO$, this is
      written $\adv^{\RO}$, and likewise for any other oracles it may have
      access to. (We do not distinguish between quantum and classical oracles
      in our notation.) Similarly, if a reduction $\bdv$ has black-box access
      to $\adv$ (meaning it may control its input and read its output, but not
      otherwise affect its internal workings), this is written $\bdv^\adv$.

  \subsubsection{Defining security.}
    The standard security notion for public-key encryption is $\indcca$, or
      ``indistinguishability under chosen-ciphertext attacks''. For the sake
      of this tutorial, we will keep it simple and stick to the weaker $\indcpa$
      (``indistinguishability under chosen-\emph{plaintext} attacks''). Since
      this is a public-key encryption scheme, the chosen-plaintext attacks can
      be performed ``off-line'' by the adversary by simply running the
      encryption algorithm itself using the provided $\pk$, and so, unlike the
      case for symmetric encryption, we do not need to provide honest
      encryptions as an oracle.

    On the left of \autoref{fig:ind-ow} is the game (or ``experiment'')
      defining the security notion in its simplest, single-user-and-challenge
      variant. The game starts by sampling parameters $\params$, a keypair
      $(\pk,\sk)$, and a challenge bit $\chalbit$, before handing the public
      key to the adversary $\adv$. If the construction in question uses a
      random oracle $\RO$ (as will always be the case here), then $\adv$
      also gets oracle access to $\RO$. At this point, $\adv$ may query $\RO$
      on whatever values it wants; in particular, these queries may depend on
      the public key $\pk$. Being a random oracle, this capability should make no
      difference to the security of the scheme (we will prove this shortly).

    At some point, the adversary will decide on two equal-length messages
      $\mssg_0$ and $\mssg_1$, and call its \emph{challenge} oracle $\Oenc$
      (\autoref{fig:ind-ow}, middle). This oracle then provides an honest
      encryption of the message $\mssg_{\chalbit}$, encoded in the challenge
      ciphertext $\chalctxt$. Note from the pseudocode that if
      the challenge oracle is ever called twice, or on messages of differing
      lengths, then it should return the special ``fail'' symbol $\fail$
      instead.\footnote{
        The requirement that $\mssg_0$ and $\mssg_1$ be equal length
        comes down to an assertion that a scheme should still be considered
        secure even if ciphertexts leak information about message \emph{lengths};
        if this requirement were not in place, then $\adv$ would be able to
        ``break'' the scheme (i.e.\ win the game) by forwarding two different-length
        messages to the challenge oracle, and learning which message
        \emph{length} the challenge ciphertext corresponds to. In fact, you may
        notice from \autoref{fig:bre} that
        our BRE scheme leaks the message length exactly, since $\demctxt$
        is guaranteed to have the same length as $\mssg$. Though we will not
        consider them here, there are
        ways of making schemes message-length-hiding, for example by padding the
        messages before encryption.
      } Now, $\adv$ may continue to call the random oracles, and this time the
      oracle calls may depend arbitrarily on $\chalctxt$ too. Once it is
      satisfied, $\adv$ halts with a guess $\advbit \in \bin$ about which message
      was encrypted, and wins if it guesses correctly.

    We measure security in terms of $\adv$'s \emph{advantage}, i.e.\ how much
      better it can do than random guessing.

    \begin{definition}[Distinguishing Advantage]
      The distinguishing advantage of an adversary $\adv$ against a
        public-key encryption scheme $\pkescheme$, under chosen ciphertext
        attacks, is defined as
      \begin{align*}
        \advantage{\indcpa}{\pkescheme} &\coloneqq \abs{
          2 \cdot \prob{\experiment{\indcpa}{\pkescheme}} - 1
        }\, ,
        \intertext{or, equivalently,}
        \advantage{\indcpa}{\pkescheme} &\coloneqq \abs{
          \prob{\experiment{\indcpa}{\pkescheme}} 
          - \prob{\neg\experiment{\indcpa}{\pkescheme}}
        }\, ,
        \intertext{or, equivalently,}
        \advantage{\indcpa}{\pkescheme} &\coloneqq \abs{
          \condprobsample{
            \experiment{\indcpa}{\pkescheme}
          }{0 \sample \adv}{\chalbit = 0}
          - \condprobsample{
            \experiment{\indcpa}{\pkescheme}
          }{0 \sample \adv}{\chalbit = 1}
        }\, .
      \end{align*}
      where $\experiment{\indcpa}{\pkescheme}[]$ is as given in
      \autoref{fig:ind-ow}.
    \end{definition}

    \noindent
    As is easiest seen from the first of the above three equations, the
      advantage is just the probability that $\adv$ wins the game, minus the
      probability of winning based on a random guess, then scaled so that the
      advantage is a value defined on the interval from $0$ to $1$ (inclusive),
      where $0$ means $\adv$ has no advantage (for example if the messages are
      information-theoretically hidden), and $1$ means that $\adv$ is a perfect
      distinguisher (the scheme is either completely broken, or $\adv$ is an
      unbounded adversary).

  \subsubsection{From one-wayness to indistinguishability.}
    It is time to prove our first theorem.

    \begin{theorem}\label{thm:bre-classical}
      Let $\kemscheme$ be a key encapsulation mechanism, let $\brescheme$ be the
      public-key encryption scheme defined in \autoref{fig:bre}, and let $\RO$ be a random oracle. 
      Then there is a SFBB reduction $\kemRed$ against $\kemscheme$ 
      for every adversary $\pkeEve$ against $\pkescheme$ satisfying
      \[
        \advantage{\indcpa}{\brescheme}[(\pkeEve^{\RO})]
        \leq 2 \cdot \qRO \cdot \advantage{\owcpa}{\kemscheme}[(\kemRed)]
      \]
      in the (classical, programmable) random oracle model. The runtime of $\kemRed$ is equal
      to that of $\pkeEve$, plus the overhead of simulating the random oracle. 
      If $\pkeEve$ makes $\qe$ calls to the challenge
      oracle, then $\kemRed$ makes $\qe$ calls to its own challenge oracle.
    \end{theorem}

    \iftutorial
    \paragraph{Interpretation.}
      Before proving the theorem, let us take a look at what the statement
        actually tells us.
        The first thing to note is the order of the quantifiers: $\exists$ reduction
        $\kemRed$ $\forall$ adversaries $\pkeEve$. At a glance, this may seem false, since
        $\kemRed$ clearly must depend on the behaviour of $\pkeEve$ in order to count as a
        reduction. However, since $\kemRed$ only
        depends on $\pkeEve$ in a \emph{black-box} manner, what we actually say
        isthat \emph{up to} the black-box dependency on $\pkeEve$, $\kemRed$ can
        be uniquely specified. 
        Another way to think of this is that $\kemRed$ comes with a number of oracle
        input/output interfaces, one of which is reserved for an adversary.

      Second, what does the bound \emph{mean}? Well, our starting assumption is that
        the key encapsulation mechanism is oneway-secure under chosen plaintext
        attacks, which means that, for every adversary,
        $\advantage{\owcpa}{\kemscheme}[(\kemRed)]$ is
        \emph{small}; hence, $\advantage{\indcpa}{\pkescheme}[(\pkeEve^{\RO})]$
        must also be small. In the asymptotic-security framework, we would say that 
        by assumption, $\advantage{\owcpa}{\kemscheme}[]$ is
        \emph{negligible}, i.e.\ smaller than any inverse-polynomial. Then the
        bound tells us that $\advantage{\indcpa}{\pkescheme}[]$ must
        also be negligible, and hence $\pkescheme$ must satisfy
        indistinguishability against chosen-ciphertext attacks. Or vice versa:
        \emph{If} there exists an adversary that breaks the indistinguishability
        of $\pkescheme$, \emph{then} we can construct an alternative attacker
        that breaks the onewayness of the underlying key encapsulation
        mechanism, contradiction our starting assumption.\footnote{
          Of course, in order to argue that $\kemscheme$ satisfies onewayness, we
          would have to further reduce it to some underlying hardness assumption,
          but those are their own whole fields of study. Indeed, ``pushing'' the
          required security assumption as far down as possible, as we do when reducing
          from indistuinguishability (stronger) to onewayness (weaker), makes
          instantiating our scheme from a variety of hardness assumptions that
          much easier. 
          To quote Hugo Krawczyk~\cite{KrawczykDistLect23}: 
          ``Modularity is the best friend of simplicity.''
        }

      Third, the right-hand-side comes with a factor of $2$. Thus, if the
        advantage of $\kemRed$ is $\half$ (meaning it guesses the correct
        preimage $50\%$ of the time), then the bound is already void, since 
        advantages are trivially upper-bounded by $1$. What this means for
        practice is that if the $\kemscheme$ scheme achieves a security level
        of, say, $2^{128}$, then the theorem only guarantees that our $\pkescheme$
        construction achieves a security level of 
        $\nicefrac{2^{128}}{2} = 2^{127}$. Of course, compensating for such
        a small tightness loss is easily done by increasing the parameters (key
        lengths etc.) by just a few bits; we will later see examples of much
        more severe tightness losses, and a large part of our goal will be to
        minimize these losses.

      \hhnote{todo: update with interpretation of $\qRO$ factor}

      Fourth, note that in the statement, $\pkeEve$ gets access to a random
        oracle $\RO$ while $\kemRed$ does not. This is because $\kemRed$ can
        easily simulate a random oracle for $\pkeEve$ by so-called
        ``lazy-sampling'', in which $\kemRed$ just samples random values for
        each new oracle call, and then stores them in a list to ensure
        consistency between calls. Alternatively, we could give $\kemRed$ access
        to a random oracle as well, and let it simply forward the oracle calls;
        once we move to the quantum random oracle model, this will be the
        preferred approach.

      Finally, in order for the bound to be meaningful, we also need to bound
        the runtime of our reduction. In this case, this is the runtime
        of the adversary itself, plus the overhead cost of lazy-sampling,
        which we can assume to be comparably small.

    \begin{proof}
      \iftutorial
      Though the reduction is conceptually fairly simple, you should
        make sure you thoroughly understand the details of the formal argument, 
        as the proof introduces several ideas that will be
        central when we move to arguing about security in the QROM.
        %such as how to use $\bad$ events to reduce to weaker notions of security.

      \fi
      The proof proceeds over four games and three game hops, outlined in
        \autoref{fig:bre-classical}: 
      \begin{itemize}
        \item $\game{0}$ is identical to the ``left-world'' $\indcpa$ game,
          i.e.\ $\experiment{\indcpa}{\pkescheme}[]$ from \autoref{fig:ind-ow}
          when instantiated with the challenge bit $\chalbit = 0$, where we have
          also ``unrolled'' the BRE construction given in \autoref{fig:bre}.
        \item $\game{1}$ is the same as $\game{0}$, except that the symmetric key
          $\demkey$ output by $\kemenc$ is overwritten by an independent value,
          ensuring that $\rnd$ and hence $\ctxt_2$ is independent of $\ctxt_1$.
          If $\pkeEve$ ever calls the random oracle on the correct symmetric key
          $\demkey$ encapsulated as part of a challenge, then they can notice
          the inconsistency (since with overwhelming probability attempting to
          thereafter decrypt $\demctxt$ will yield neither $\mssg_0$ nor
          $\mssg_1$). This is captured by the $\bad$ event, which if ever hit
          upon causes the game to abort.
        \item $\game{2}$ is the same as $\game{1}$, except that the challenge oracle
          now encrypts the ``right-world'' message $\mssg_1$.
        \item $\game{3}$ is the same as $\game{2}$, except that the symmetric key
          $\demkey$ is no longer overwritten, removing the need for a $\bad$ event,
          making $\game{3}$ identical to the ``right-world'' $\indcpa$ game when
          instantiated with the BRE construction.
      \end{itemize}

      \noindent
      We analyze the game hops using \autoref{lemma:game-hopping}:
      \begin{align*}
        \advantage{\indcpa}{\brescheme}[(\pkeEve)] &\coloneqq 
          \abs{
            \condprobsample{
              \experiment{\indcpa}{\brescheme}[(\pkeEve)]
            }{0 \sample \adv}{\chalbit = 0}
            - \condprobsample{
              \experiment{\indcpa}{\brescheme}[(\pkeEve)]
            }{0 \sample \adv}{\chalbit = 1}
          } \\
        &= \abs{
          \probsample{\game{0}(\pkeEve)}{0 \sample \pkeEve}
          - \probsample{\game{3}(\pkeEve)}{0 \sample \pkeEve}
        } \\
        &\leq \abs{
          \probsample{\game{0}(\pkeEve)}{0 \sample \pkeEve}
          - \probsample{\game{1}(\pkeEve)}{0 \sample \pkeEve}
        } \\
        &\quad + \abs{
          \probsample{\game{1}(\pkeEve)}{0 \sample \pkeEve}
          - \probsample{\game{2}(\pkeEve)}{0 \sample \pkeEve}
        } \\
        &\quad + \abs{
          \probsample{\game{2}(\pkeEve)}{0 \sample \pkeEve}
          - \probsample{\game{3}(\pkeEve)}{0 \sample \pkeEve}
        }\, .
      \end{align*}

      \noindent
      For the first game hop, note how $\game{0}$ and $\game{1}$ are identical,
        except for the real symmetric key being exchanged for a random one. This
        is reminiscent of the IND-CPA experiment for key encapsulation
        mechanisms, and indeed if $\pkeEve$ can tell the difference between the
        games, then a reduction can use this to break $\indcpa$ for the
        underlying KEM.

      However, since we are in the random oracle model, we can do one better: If
        $\pkeEve$ can tell the difference between $\game{0}$ and $\game{1}$, then 
        a reduction can break the \emph{onewayness} of the underlying KEM,
        recovering the symmetric key $\demkey$. How? Simple: Just store the
        adversary's inputs to the random oracle, and output one of them at random.
        If $\pkeEve$ has a distinguishing strategy, then that strategy must
        involve calling the random oracle on the symmetric key encapsulated in
        $\kemctxt$, since the only way to tell the games apart is by breaking
        $\kemctxt$, reconstructing $\demctxt$, and checking for consistency.
        Then, since $\pkeEve$ makes at most $\qRO$ calls to the random oracle,
        the reduction will output the correct value with probability at least
        $\nicefrac{1}{\qRO}$.

          \pchspace

          \procedure{If $\pkeEve$ calls $\RO_\ell(x)$}{
            \pcif \pcparse x = (\pk, \demkey, \ctxt) \pcthen \\
              \t \pcif \ctxt \in \Cspace \pcthen \keyset \setapp \demkey \\
            \pcwhile \abs{\Hlist[x]} < \ell \pcdo \\
              \t \Hlist[x] \listapp \bin \\
            \pcreturn \Hlist[x]\elms{\ell}
          }

      After moving to $\game{1}$, the DEM
        ciphertext $\demctxt$ is independent of the KEM ciphertext $\kemctxt$,
        meaning that the only way for $\pkeEve$ to learn whether $\demctxt$
        contains $\mssg_0$ or $\mssg_1$ is to study $\demctxt$ itself.
        However, the message has been encrypted with the one-time pad, using a
        value that is guaranteed to be uniformly random, by the definition of
        a random oracle. Hence, the message is perfectly
        (information-theoretically) hidden from
        the view of $\pkeEve$, which implies that
      \[
        \abs{
          \probsample{\game{1}(\pkeEve)}{0 \sample \pkeEve}
          - \probsample{\game{2}(\pkeEve)}{0 \sample \pkeEve}
        } = 0\, .
      \]

    \end{proof}
