    \subsubsection{Security Games.}
    	Security is defined in terms of a \emph{security game}.
      	You can envision these as a game in which a player (or \emph{adversary})
      	is challenged to break security of a cryptographic construction (or \emph{primitive}),
      	where the win conditions of the game captures what ``breaking'' means in the specific context.
      	%
      	More formally, we will model the ``player''/``adversary'' as an
        algorithm $\adv$.\footnote{
          In technical terms, $\adv$ is assumed to be a probabilistic (or quantum) Turing machine.
        }
      	%\khnote{I'd usually use $\mathcal{A}$, but that's a matter of taste.}
        %% Done. --H
        A security game $\examplegame$ is a program, usually written in pseudocode, %$\experiment{}{}[]$ 
        that interacts with $\adv$ by running it as a black-box subroutine; see
        \cref{fig:example-game} for an example.
        $\examplegame$ will use  $\adv$ as a \emph{black-box}, meaning it can
        only provide inputs to and receive outputs from $\adv$,
      	because we do not want to make any assumptions about $\adv$'s potential
        attack strategies. This way, we can confidently say that our security experiment considered
      	\emph{any} kind of attack that aimed to break the formalized security goal.
      	At the end, $\examplegame$  will finish by outputting a bit
      	that depends on the interaction with $\adv$, to indicate if $\adv$ managed to break security.

      Any security game is defined to express security of some primitive
        $\primitive$, for example a particular public-key encryption (PKE) scheme.
      	Thus, part of the experiment's code uses the algorithms of the primitive
        $\primitive$ whose security we want to express.
      	E.g., we might want to write an experiment to express that encryptions of a PKE scheme \PKE
      	are ``one-way'' in the sense that they are hard to invert without the secret key.
      	To express this, the ``\textbf{\underline{O}}ne-\textbf{\underline{W}}ayness under \textbf{\underline{C}}hosen-\textbf{\underline{P}}laintext \textbf{\underline{A}}ttacks'' game
        \owcpa would encrypt a random plaintext message \chalmssg into a ciphertext \chalctxt,
      	hand \chalctxt to $\adv$,
      	have $\adv$ output a guess \advmssg,
        and return 1 if $\adv$ guessed the correct encrypted message (so if $\advmssg =
        \chalmssg$). This is the example formalized in \cref{fig:example-game}.

      Like all common definitions of security, the $\owcpa$ definition is intended to be \emph{generic},
      	meaning it can capture this type of security for \emph{any} kind of PKE scheme.
      	To account for that, the game's template uses abstract placeholders for the specifics of \PKE, like
      	\KG for the key generation, \Enc for the encryption algorithm,
      	and \Mspace for the space of messages that \PKE can encrypt.
      	If we want to express security of, say, ElGamal encryption, we would
        fill in the specifics of ElGamal at the respective places.
      	For any security game filled in with the specific algorithms of a concrete primitive $\primitive$,
      	we will write $\experiment{Game}{\primitive}$.
      	We will say that adversary $\adv$ wins the game $\experiment{Game}{}[]$
        for a specific construction of primitive $\pcalgostyle{P}$
        if $\experiment{Game}{\primitive}$ outputs $1$.
        We will denote this event by $\experiment{Game}{\primitive} \Rightarrow 1$.
        In that case, we will also say that adversary $\adv$ broke the
        $\experiment{Game}{}[]$ security of primitive $\primitive$.
        
      Security games are typically named by the convention that the letters
	      preceding the hyphen defines a security \emph{goal} that we would like our 
	      primitive \primitive to achieve\khnote{use xspace in macro for \primitive}, and the letters after the hyphen lists the
	      attack \emph{power} of the adversaries with respect to which it will
	      achieve that security goal: so $\goalpow$. In the example of $\owcpa$, the
	      \emph{goal} is the one-wayness of encryption, while the adversary's \emph{power} is
	      chosen plaintext attacks (\pcnotionstyle{CPA}), i.e.\ the power to generate encryptions
	      at will of any message it likes. Since this example deals with public-key
	      encryption, this power is given for free, and so this is the minimal
	      power that the adversary can have for a well-defined notion of PKE
	      security. For other primitives the adversary
	      could have less attack power: consider for example symmetric
	      encryption, where you need to know the secret key to encrypt.
	      In other words, if attackers are not handed the secret key,
	      than they cannot produce encryptions on their own.
	      It would thus be plausible to formalize the idea that a symmetric scheme is one-way,
	      restricted to the requirement that the attacker never got to see an encryption.
	      This weakest notion for symmetric encryption might then be
	      called \ownma, for ``no message attack''.
      
      \paragraph{The Strength of a Security Notion.}
        What do we mean when we say that a notion such as \ownma would be ``weak''? Well,
          in general the \emph{strength} of the notion scales with how ``easy'' it
          would be for a sufficiently strong adversary to win the game:
          A security notion with a simpler \emph{goal}, such as guessing
          which of two known messages are encrypted (this is known as
          \emph{indistinguishability}, or \ind) is stronger than one with a more complex
          goal, such as recovering the full message from scratch like in the above
          example: We have lowered the bar for what counts as ``breaking'' the scheme, so if
          no adversary can win at the easier game, then
          there certainly aren't any adversaries that can win at the harder one
          either. Hence, claiming security under an easier-to-break goal gives a
          \emph{stronger} statement. 

        The other lever with which we can control the
          strength of a security notion is of course the attack power given to the
          adversary: more power means a stronger security notion. For
          example, consider again the case of symmetric encryption: we could give
          the adversary the power of chosen-plaintext attacks by simply
          \emph{providing} it with encryptions of its choosing whenever it asks.
          The claim that the game \emph{still} can not be won by any adversary is
          stronger than claiming that it can not be won without this ability.

        So: \ownma is a weaker notion of security than \owcpa, with \indcpa
          stronger still. Meanwhile, \owcpa and \indnma would in general be
          \emph{incomparable} in terms of strength: A symmetric encryption scheme
          might be secure with respect to one notion while being
          completely broken in terms of the other.\footnote{
            It is a fun puzzle to try to come up with encryption schemes that exemplify this
            behaviour (secure under one notion, insecure under the other);
            a little creative thinking should allow you to find some. (Hint:
            As a starting point, assume that you have an encryption scheme that
            is secure under both notions, then think
            about how you could alter it so that it ``breaks'' under one notion
            but not under the other.)
          }

      \subsubsection{Advantages.}
        Intuitively, a primitive $\primitive$ is ``broken'' if there exists an
          ``efficient'' adversary (i.e., an ``efficient'' attack algorithm)
	        that wins the game with a ``significant'' probability,
	        and it is ``secure'' if no such adversary exists.
	        (You could think of ``efficient'' attacks as attacks whose running time doesn't blow up catastrophically
	    	  if we increase the construction's parameters, like, e.g., the key length.
	    	  Similarly, you could think of ``significant'' probabilities as probabilities that do not speed-run towards 0
	    	  upon parameter increase.)

        Under the paradigm of \emph{asymptotic security}, one would identify
          ``efficient'' with ``scales as a polynomial in the security
          parameter'', with similar definitions for ``significant''
          probabilities. In practice, however, cryptographic designs need to
          make concrete parameter choices,
	        and such asymptotic notions do not necessarily help with assessing how secure the concrete design is in practice.
	        We will thus follow the \emph{concrete security} approach, 
          expressing security via explicit bounds that relate the adversary’s
          resources to its probability of successfully breaking our scheme.
          This success probability is captured by the notion of an \emph{advantage},
          which could for example be the probability that an attacker can find the original
          message \chalmssg belonging to a ciphertext \chalctxt.
          
        How the advantages are defined depends on what kind of security
          notion we are talking about.
          The security notions we care about all fall into one of two categories:
        
        \begin{itemize}
        	\item \emph{Finding},
        		%\khnote{
            %  Replaced "computational" with "finding" because distinguishing
            %  problems are also "computational" in the sense that they're not
            %  information-theoretic.
            %} % makes sense
        		in which case the adversary is tasked with finding some secret value
        		(like our ciphertext inversion example). Here, 
        		advantages will usually be taken to simply be the win probability:
        		\[
	        		\advantage{\findnotion}{\primitive} \coloneqq
	        		\prob{\experiment{\findnotion}{\primitive} \Rightarrow 1}\, .
        		\]
        	\item \emph{Distinguishing},
	        	in which case the adversary is tasked with distinguishing between two scenarios.
        		(E.g., the adversary might need to distinguish a real encryption
            from a ciphertext that was chosen uniformly at random.)
        		Here, the expected output of $\adv$ is a bit, to indicate its guess
            about which scenario (or ``world'') it interacted with.
        \end{itemize}
        
        \noindent
        In ``distinguishing'' notions, any adversary can win with probability
          $\half$ by simply making a random guess (since it will be in each of the
          two worlds with equal probability).
          Thus, we would like the adversary's \emph{advantage} to capture how much
          \emph{better} the adversary can do than randomly guessing.
          There are several, equivalent ways to do this, and it will 
          sometimes be useful to switch between them.

        One standard way of defining distinguishing advantages is the following:
          \[
          	\advantage{\distnotion}{\primitive} \coloneqq \abs{
          		2 \cdot \prob{\experiment{\distnotion}{\primitive} \Rightarrow 1} - 1
          	}\, .
          \]
          Here, the game internally tosses a coin to determine which of the
          two to-be-distinguished worlds the adversary will be interacting
          with, and the game outputs $1$ if the adversary guessed the correct
          world. Note how scaling by a factor $2$ and subtracting $1$
          makes the advantage a value that runs between $0$ (for strategies that are no
          better than guessing) to $1$ (for strategies that always win),
          matching the ``finding'' case.

        Equivalently, you could split the experiment into the two
          to-be-distinguished scenarios.
          To do so, you can capture the outcome of the coin toss as a
          ``challenge bit'' $b$, condition the experiment on $b$,
          and quantifying how much more (un)likely it is that $\adv$ outputs $1$
          in the one setting than the other:
          \[
          	\advantage{\distnotion}{\primitive} \coloneqq \abs{
          		\condprobsample{
          			\experiment{\distnotion}{\primitive}
          		}{1 \gets \adv}{\chalbit = 0}
          		- \condprobsample{
          			\experiment{\distnotion}{\primitive}
          		}{1 \gets \adv}{\chalbit = 1}
          	}\, .
          \]

    \subsubsection{Public-Key Encryption.}
      The quest for asymmetric cryptography began with Diffie and Hellman's idea
        of public-key encryption~\cite{DifHel76}, so fittingly this is also where we
        begin.

	    \begin{definition}[Public-Key Encryption]\label{def:PKE}
	    	A public-key encryption scheme $\PKE = (\KG, \Enc, \Dec)$ is a triple of algorithms
	    	defined with respect to public-key space \PKSpace, secret-key space \SKSpace,
	    	message (plaintext) space \MSpace, ciphertext space \CSpace, and randomness space \RSpace.
	    	More precisely, the triple of algorithms is defined as follows.
	    	\begin{itemize}
	    		\item
            $\KG(\, ) : (\pk, \sk) \in \PKSpace \times \SKSpace$.
	    			Probabilistic algorithm that takes no input and outputs a ``keypair'' $(\pk, \sk)$.
	    		\item
	    			$\Enc(\pk \in \PKSpace, \mssg \in \MSpace) : \ctxt \in \CSpace$.
	    			Probabilistic algorithm that, given a public key $\pk$ and message $m$,
	    			produces an ``encryption'' (``ciphertext'') $\ctxt$ of $\mssg$ under $\pk$.
	    			We may explicitly specify the randomness used in encryption by
            writing $\Enc(\pk, \mssg; \rand)$, where $\rand \in \RSpace$.
	    		\item
	    			$\Dec(\ctxt \in \CSpace, \sk \in \SKSpace) : \mssg \in \MSpace \cup \{\bot\}$.
	    			Deterministic algorithm that, given a secret key $\sk$ and ciphertext $\ctxt$,
	    			yields either a message $\mssg \in \MSpace$ or an explicit failure symbol $\bot \notin \MSpace$,
	    			the latter indicating that $\ctxt$ is not a valid ciphertext (under $\sk$).
	    	\end{itemize}
	    \end{definition}
	    
      \noindent
      To ease readability, we will use the convention that the ``key'' part
        of the input is provided as a subscript, so $\Enc_\pk(\mssg) \coloneqq
        \Enc(\pk,\mssg)$ and $\Dec_\sk(\ctxt) \coloneqq \Dec(\sk, \ctxt)$.
      %%%% (No longer needed if we're skipping parameters)
        %First, whenever some object is generated
        %dependent on some other public object, such as the public key $\pk$ being
        %dependent on the public parameters $\params$ (which in turn depend on the
        %security parameter $\secpar$), we assume without loss of generality that
        %the new object includes descriptions of the prior (public) objects (so if you
        %know $\pk$, then you also know $\params$). Similarly, we assume
      We will also use the convention that if you know a secret key $\sk$ belonging to a
        keypair $(\pk, \sk)$, then you also know $\pk$. This is w.l.o.g.\ in the sense
        that after a keypair $(\pk,\sk)$ is generated, you can always re-define the
        keypair to instead be $(\pk, (\pk, \sk))$ (though it enforces
        a unique-public-key-per-secret-key relation,
        and there exist PKE schemes that violate this~\cite{EC:BelHofYil09}).

      As mentioned, we require that $\PKE$ exhibits perfect correctness:
      \[
        \forall\, \mssg\in\MSpace:\ \probsample{
          (\pk,\sk) \sample \KG, \ctxt \sample \Enc_\pk(\mssg)
        }{
          \Dec_\sk(\ctxt) = \mssg
        } = 1\, ,
      \]

      \noindent
      and we also require perfect
      \emph{rigidity}~\cite{EPRINT:BerPer18,EC:HHMS25}, which can be thought of
      as the reverse direction of perfect correctness,
      and which says that there are no ciphertexts in $\CSpace$ that successfully decrypt
      under $\sk$, yet can not be reproduced as an encryption of the decrypted
      message under $\pk$:
      \[
        \forall\, \ctxt\in\CSpace:\ \probsample{
          (\pk,\sk) \sample \KG,\ \mssg \gets \Dec_\sk(\ctxt)
        }{
          \mssg \neq\, \perp \land\
          \forall_{\rand\in\RSpace}\, \Enc_\pk(\mssg; \rand) \neq \ctxt
        } = 0\, .
      \]

    \subsubsection{Key Encapsulation Mechanisms.}
      A key encapsulation mechanism is a public-key primitive that samples a
        symmetric key, encrypts (or \emph{encapsulates}) it, and returns both.

	    \begin{definition}[Key Encapsulation Mechanism]\label{def:KEM}
	    	A key encapsulation mechanism $\KEM = (\KG,$ $\Encaps,$ $\Decaps)$ is a triple of algorithms
	    	defined with respect to public-key space \PKSpace, secret-key space \SKSpace,
	    	symmetric key space \KSpace, and encapsulation space \CSpace.
	    	More precisely, the triple of algorithms is defined as follows.
	    	\begin{itemize}
	    		\item
	    			$\KG() : (\pk, \sk) \in \PKSpace \times \SKSpace$.
	    			Probabilistic algorithm that takes no input and outputs a ``keypair'' $(\pk, \sk)$.
	    		\item
	    			$\Encaps(\pk \in \PKSpace) : (K, c) \in \KSpace \times \CSpace$.
	    			Probabilistic algorithm that, given a public key $\pk$,
	    			produces a tuple $(c,\KEMoutputKey)$,
	    			where $c$ is said to be an ``encapsulation'' of the key $\KEMoutputKey$.
	    		\item
	    			$\Decaps(\sk \in \SKSpace, c \in \CSpace) : \KEMoutputKey \in \KSpace \cup \{\bot\}$.
	    			Deterministic algorithm that, given a secret key $\sk$ and ciphertext $c$,
	    			yields either a key $\KEMoutputKey \in \KSpace$ or an explicit failure symbol $\bot \notin \KSpace$,
	    			the latter indicating that $c$ is not a valid ciphertext (under $\sk$).
	    	\end{itemize}
	    \end{definition}

      \noindent
      It is easy to see that a KEM can be built from any PKE, by first sampling
        a symmetric key and then encrypting it. In the other direction, a PKE can be built
        from a KEM by combining it with any symmetric encryption scheme (such as
        AES), so that the KEM encapsulates a symmetric key, and the symmetric
        scheme encrypts the message. In this context, the symmetric scheme
        is referred to as a ``DEM'', for ``Data Encapsulation Mechanism'',
        and the resulting PKE is called a ``KEM-DEM hybrid encryption scheme''.
        Since symmetric keys are typically much shorter than messages,
        such PKEs are usually a lot more efficient than using the underlying PKE
        scheme to encrypt the message directly, 
        owing to the superior efficiency of symmetric encryption.

    \subsubsection{Hash Functions.}
      A hash function $\RO: \bin^* \to \bin^m$ is a deterministic but random-looking 
        function that takes inputs of any size, and returns a comparably small
        ``fingerprint'', or \emph{digest}, of that input.\footnote{
          Technically, then, a hash function is a \emph{family} of functions,
          one for each input length.
        } Hash functions are ubiquitous in computing: As just one example out of
        many, they can be used to efficiently check if two large files are
        equal, by simply comparing their much smaller ``fingerprints'' instead.

      Cryptography puts strict requirements on hash functions, and we
        demand that any cryptographic hash function should satisfy
        \emph{one-wayness} and \emph{collision resistance}. We will define these
        shortly, though it is perhaps easy to see that a uniformly random
        function should satisfy both (for large enough $m$). This is relevant,
        as hash functions are precisely the objects that we will model as
        random oracles in \cref{sec:rom}.

    \subsubsection{PKE Security.}
      There are many ways that one could define security for
        public-key encryption, but a few have emerged as standard.

      \paragraph{One-Wayness.}
        At minimum, a secure PKE scheme must hide the message being encrypted.
          We can formalize this as ``One-Wayness under Chosen-Plaintext Attacks'',
          or $\owcpa$, where ``under Chosen-Plaintext Attacks'' is simply
          to say that anyone with access to a public key can use it to generate
          ciphertexts for any message they wish.

        The one-wayness game is shown to the left in \cref{fig:pke-games}. As
          you can see, the game is defined in pseudocode. With experience, you
          will learn to skim pseudocode-games like these to quickly
          grasp the main concepts, but in case you are new to security games,
          here are a few things to notice:
          \begin{itemize}
            \item The encrypted message $\mssg$ is sampled uniformly at random 
              at the start of the game, before the adversary is ever invoked,
              and so the adversary can not influence the distribution that the
              message was sampled from at all.
              This should be considered a weakness of the notion, since less
              adversarial power $\to$ weaker security guarantees:
              What if some messages are known to give insecure ciphertexts?
            \item The adversary (who is a Turing machine) is called as a subroutine exactly
              once in a black-box manner, meaning that once they are given an input,
              the game only continues once they halt with an output. Also
              notice that the adversary is not given access to any oracles.
            \item The adversary is only given a single challenge ciphertext, in
              addition to the public key. More general security notions might
              allow the adversary to receive many challenge ciphertexts, and maybe even
              multiple public keys, and allow it to win if it reverses any one of them.
          \end{itemize}

        \begin{definition}[OW-CPA]\label{def:owcpa}
          The one-wayness advantage $\advantage{\owcpa}{\pkescheme}$ of an
          adversary $\adv$ against a public-key encryption scheme $\pkescheme$
          is the "find" advantage (\cref{def:find-adv}) of $\adv$ in the
          $\owcpa$ game (\cref{fig:pke-games}, left) when instantiated with the
          scheme $\pkescheme$.
        \end{definition}

        \newcommand{\skucpa}{\pcnotionstyle{SKU}\hy\cpa}
        One question that one might ask is, in terms of computational security
          notions for public-key encryption, is it not more natural to define a
          game where the adversary wins if it can compute the secret key from the public key? 
          Well, this is a perfectly valid notion of security---let's call
          it SKU, for ``Secret-Key Unrecoverability''. 
          As before, since anyone can encrypt messages, 
          the adversary has the power of Chosen-Plaintext Attacks, and so we get
          the security notion $\skucpa$.

        Notice, though, that anyone who can compute the secret key from the public
          key, can also decrypt any ciphertext that were created using that public
          key. This means that if an adversary $\adv$ can recover secret keys,
          then they can also win the \owcpa game, whereas
          the opposite does not seem to hold in general (since there might be
          ways to attack a ciphertext that does not rely on knowing the secret
          key). Hence, $\owcpa$ gives a \emph{stronger} security guarantee than
          $\skucpa$, since if one-wayness is satisfied, then 
          secret-key unrecoverability must also be satisfied.
          We say that $\owcpa$ \emph{implies} $\skucpa$.

        Proving implications like the above is one of the core activities of provable
          security, so though the statement may seem trivial, let's try our hand
          at proving it.

        ``Indistinguishability under Chosen-\emph{Plaintext} Attacks'' ($\indcpa$). Since
        this is public-key encryption, any adversary can generate as many

  \subsection{Reductions}
    The main tool we have in proving security is that of a \emph{security
      reduction} (\ldots)
    
    \hhnote{skip the following?}

    We say that a reduction is \emph{simple} if it only runs the adversary once,
      and \emph{fully black-box} if it only accesses the adversary and
      cryptographic primitives in black-box ways,
      running the adversary from start to finish without tampering with its
      internal workings, answering oracle queries along the way, and otherwise
      only providing its input and reading its output.
      %; if, as is typically the case, the reduction is both simple and fully
      %black-box, we call it an SFBB reduction.
      In contrast, a reduction might for example \emph{rewind} an adversary,
      running it several times to figure out how it \emph{would} behave given
      different inputs; such a reduction would not be considered simple.
      Generally speaking, simple, fully black-box reductions are preferred, as
      they are more general and easier to work with, but such reductions are not
      always possible to construct.

    Since simple, fully black-box reductions only access the adversary in a
      black-box manner, they do not depend on the specific workings of the
      adversary, and may therefore be quantified before it.

    %We will later see some reductions that \emph{rewind} the adversary, and run

    \hhnote{TRIVIAL REDUCTION EXAMPLE TO SHOW THE FRAMEWORK: IND $\to$ OW}

    If, given a ciphertext, you have the ability to break encryption and recover the
      underlying plaintext, then you can also distinguish which of two
      ciphertexts were encrypted. When talking about reductions between security
      notions, we usually state the contrapositive: that
      ``\emph{indistinguishability} (the inability to distinguish) implies
      \emph{one-wayness} (the inability to recover plaintexts)''. 

    Let us prove this simple fact as a demonstration of how
      we usually construct security reductions.

    \begin{theorem}[IND $\To$ OW]\label{thm:ind-ow-red}
      Let $\pkescheme$ be any public-key encryption scheme. Then there exists a
      simple, fully black-box reduction $\bdv$, such that for every adversary $\adv$,
      \[
        \advantage{\owcpa}{\pkescheme} \leq
        \advantage{\indcpa}{\pkescheme}[(\bdv^{\adv})]\, ,
      \]
      where $\bdv$ runs in the same time as $\adv$.
    \end{theorem}

    \paragraph{Parsing the Statement.}
      \hhnote{cut-and-pasted from the next section}
      If you are new to security reductions, it may be hard to see at a glance
        how the theorem statement connects to the intuition that ``if
        $\dPKE$ achieves one-wayness security, then $\KEM$ achieves distinguishing
        security'', so let us take a moment to parse the different parts of the
        statement.

      On the left-hand side of the main inequality, we have the distinguishing
        advantage of our given adversary $\adv$.
        The theorem quantifies over all possible $\adv$, so you may
        think of this as the maximum possible distinguishing advantage against
        the construction. On the right-hand side, we have an upper-bound on this
        largest-possible distinguishing advantage. Hence,
        if the right-hand side is small, then the largest-possible
        distinguishing advantage against $\KEM$ must also be small. This is
        just a different way of saying that $\KEM$ is indistinguishable.
        The term on the right-hand side is the one-wayness advantage of our
        \emph{constructed} adversary $\bdv$. Note the quantifiers: the theorem
        statement says that ``for every (given) $\adv$, there exists a
        (constructed) $\bdv$''. Hence, while we have no way of knowing the inner
        workings of the given adversary $\adv$, we are free to construct $\bdv$ to our
        liking. 

      The trick to understand how this ``proves security'' is to think
        contrapositively. Recall that what we
        want to prove is that ``if $\dPKE$ is secure, then $\KEM$ is secure''.
        The conrapositive statement that we are actually proving is ``if $\KEM$
        is \emph{in}secure, then $\dPKE$ must \emph{also} be insecure''. 
        Hence, instead of thinking of $\bdv$'s advantage as
        an upper-bound on the best-possible $\adv$ advantage, think of this
        best-possible $\adv$ advantage as a \emph{lower-bound} on the
        advantage an adversary $\bdv$ could achieve against $\dPKE$: If the
        former is large (\KEM is broken),
        then the latter must also be large (\dPKE is broken).
        Since we started out assuming that $\dPKE$ is secure, 
        %which is to say that the one-way advantage of \emph{any} $\bdv$ must be small, 
        this gives us our proof-by-contradiction.

    \subsubsection{Game Hopping.}
      \hhnote{
        copy-pasted from \cref{sec:basics}
      }
      %\todoenum[Provide explanations of:]{
      %  \item Basic background on game hopping and advantages, stuff like
      %    difference vs.\ times two minus 1, with or
      %    without absolute values, the fundamental lemma of game hopping.
      %  \item Maybe write something about asymptotic vs.\ concrete security.

      For our security proofs, we will be working in the game-hopping
        paradigm of Shoup~\cite{EPRINT:Shoup04}.
        The fundamental lemma of game hopping states that the distinguishing advantage
        of an adversary can be bounded in terms of their distinguishing advantage
        over several intermediary game ``hops''.

      \begin{lemma}\label{lemma:game-hopping}
        For any adversary $\adv$ tasked with distinguishing $\game{0}$ from
        $\game{n}$, and for any games $\game{1}, \ldots \game{n-1}$,
        there exist adversaries $(\adv_1, \ldots, \adv_n)$ such that
        \[
          \abs{
            \probsample{\game{0}(\adv)}{1 \sample \adv} -
            \probsample{\game{n}(\adv)}{1 \sample \adv}
          } \leq \sum_{i = 1}^n \abs{
            \probsample{\game{i-1}(\adv)}{1 \sample \adv_i} -
            \probsample{\game{i}(\adv)}{1 \sample \adv_i}
          }\, .
        \]
      \end{lemma}

      \noindent
      The lemma states that, if $\adv$ were able to distinguish, then
        at least one of $\adv_1, \ldots, \adv_n$ must be able to
        distinguish too---and vice versa, that if none of the $\adv_i$ are able to
        distinguish, then neither is $\adv$.
        (In fact, the $\adv_i$ that achieve this will in essence be just copies
        of $\adv$.)

      The proof is remarkably simple, reproduced here for those who haven't
        seen it.

      \begin{proof}
        For all $i$ from $1$ to $n-1$, insert $0 = \probsample{\game{i}(\adv_i)}{1 \sample \adv_i} -
        \probsample{\game{i}(\adv_i)}{1 \sample \adv_i}$ into the absolute value
        on the left hand side, then apply the union bound.
        \qed
      \end{proof}

      \hhnote{

      \hhnote{

      %% Restatable Lemma usage: 
        %% \begin{restatable}[Header]{environment type}{thm-restate reference string}\label{cref label}
        \begin{restatable}[Equivalent-Until-Bad]{lemma}{equbad}\label{lemma:equbad}
          xyz
        \end{restatable}

      Let us use the law of total probability (and the triangle inequality
        again) to split into two distinguishing advantages, one for
        the case that $\bad$ is set to $\true$ and one for the case that $\bad$
        remains $\false$.
        \begin{align*}
          \advantage{\indcpa}{\KEM} &\leq 
            \abs{ \probsample{ \game{2}(\adv) }{1 \gets \adv \land \neg \bad} 
              - \probsample{ \game{3}(\adv) }{1 \gets \adv \land \neg \bad}} \\
            &\qquad + \abs{ \probsample{ \game{2}(\adv) }{1 \gets \adv \land \bad} 
              - \probsample{ \game{3}(\adv) }{1 \gets \adv \land \bad}}\, .
        \end{align*}
        These distinguishing advantages represent the probability that the adversary notices
        that we are exchanging the real key for a random key. Notice that
        $\dPKE$ being deterministic and correct imposes a one-to-one
        correspondence between messages and ciphertexts. This means that if $\bad$ 
        is never set to $\true$, then re-encryption never yielded $\chalctxt$,
        which in turn implies that the random oracle was never called on $x^*$. 
        Thanks to the uniform nature of random oracles, this means that 
        both real and random $\eK^*$ will look completely random from the
        point of view of $\adv$. Hence, the two probabilities 
        $\probsample{ \game{2}(\adv) }{1 \gets \adv \land \neg \bad}$
        and
        $\probsample{ \game{3}(\adv) }{1 \gets \adv \land \neg \bad}$
        are equal, and the $\neg \bad$ part of the distinguishing advantage is
        zero:
        \begin{align*}
          \advantage{\indcpa}{\KEM} &\leq 
            \abs{ \probsample{ \game{2}(\adv) }{1 \gets \adv \land \bad} 
              - \probsample{ \game{3}(\adv) }{1 \gets \adv \land \bad}}\, . 
        \end{align*}
        We have reached the crux of the matter: The distinguishing
        advantage of $\adv$ can be characterized as the difference in its
        probability of outputting $1$ \emph{and} in calling the random oracle on
        the correct $x^*$. But notice that 1) up until the point that $\bad$ is set to
        $\true$, $\eK^*$ will look completely random to $\adv$, and 2) \emph{after}
        $\bad$ is set to $\true$, an adversary would easily be able to
        distinguish, e.g.\ by using $\dPKE$ to
        re-encrypt $x^*$ and confirm that it gives the correct
        $\chalctxt$, then comparing $\eK^*$ against $\RO(x^*)$.
        We therefore lose nothing of significance if we simply bound this
        distinguishing advantage by the probability that $\bad$ is set to $\true$.
        \begin{align*}
          \advantage{\indcpa}{\KEM} &\leq 
            \probsample{ \game{2}(\adv) }{\bad} 
              = \probsample{ \game{3}(\adv) }{\bad}\, ,
        \end{align*}
        where, again, the latter equality holds due to the view of $\adv$ being equal
        in both games up until the point that $\bad$ is set to $\true$, since
        random oracles are perfectly preimage-hiding.
